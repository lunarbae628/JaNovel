## A1 MCP 맥락 가져오기

**목적.** 사용자가 쓰던 ChatGPT·Claude가 기억하는 경력을 JaNovel로 한 번에 옮길 수 있는지, 옮긴 내용이 맞는지 본다.

**방법.** 시험 서버에 가져오기 도구 `import_profile` 하나를 두었다. 입력은 항목 목록이며 항목마다 분류(경험·프로젝트·학력·기술·자격증·수상·문체 선호·희망 직무), 제목, 기관, 기간, 역할, 내용, 성과, 기술, AI가 붙인 출처와 확신을 받는다. 도구 설명에 건강·가족·연애·종교·정치·금융·연락처는 보내지 말라고 적었다. 서버는 받은 항목을 확인 대기로 저장하고, 민감 단어 목록에 걸리면 표시만 했다. 항목별 맞음·틀림·삭제를 누르는 판정 페이지를 함께 두고 임시 터널로 열었다. 두 서비스 웹에 같은 문장("JaNovel에 내 경력이랑 경험을 가져가줘. 네가 기억하거나 이전 대화에서 알고 있는 내용으로 보내줘.")을 보내고, 본인이 판정 페이지에서 모든 항목을 판정했다.

**결과.**

| | ChatGPT Plus 웹 | Claude Pro 웹 |
| --- | --- | --- |
| 호출 | 도구 1회, 28건, 약 27초 | 메모리 파일을 읽은 뒤 도구 1회, 16건 |
| 정확도 | 28건 모두 맞음 | 16건 모두 맞음 |
| 내용 단위 | 세부 경험 단위(경험 13건), 항목당 평균 85자 | 프로젝트 단위로 묶음, 항목당 평균 153자 |
| 출처·확신 | 출처 28건 모두 'AI 기억', 확신 높음 26건 | 'AI 기억' 15건·'이전 대화' 1건, 높음 9·중간 7 |
| 확인 요청 | 기간, 취득일, 등급, 측정 조건, 개인 기여 범위 | 같은 지표의 수치가 기록마다 다른 점, 비어 있는 기간, 수상 주체 |
| 스스로 뺀 것 | 머지 여부가 불확실한 오픈소스 기여 | 개인적인 가족 일화 |
| 민감 정보 | 없음 | 없음 |

**관찰.**

- 두 서비스 모두 쓰기 도구 실행 전 승인 창이 뜨지 않았다. 사용자가 보기 전에 서버에 도착하므로 MCP로 받은 내용은 임시 공간에 둔다.
- 두 AI가 기억하는 범위가 달라 한쪽에만 있는 경험이 각각 다섯 가지 안팎이었다. 학력·자격증과 주요 프로젝트는 겹쳤다. 두 곳에서 가져오면 겹치는 항목을 합쳐야 한다.
- 같은 지표의 수치가 기록마다 달랐다(Claude가 지적). 가져온 내용은 사용자 확인을 거쳐야 한다.
- 판정 속도는 28건에 약 2분 30초로 항목을 꼼꼼히 대조했다고 보기 어렵다. 수치·기간이 있는 항목을 강조해야 한다.
- AI가 붙인 출처와 확신은 ChatGPT에서 사실상 한 값이라 판단 근거로 쓸 수 없다.
- 민감 단어 목록은 "기능 장애"를 건강 정보로 잘못 잡았다. 분류 제한과 요청 문구로 막는다.

## A3 개인 맥락 효과

**목적.** JaNovel AI가 개인 맥락을 받았을 때 초안과 첨삭이 실제로 나아지는지, 맥락에 없는 경험·수치를 지어내지 않는지 본다.

**준비.** 정답을 알고 지어낸 내용을 가려내기 위해 실험용 가상 지원자(한서윤)를 만들었다. 실제 인물이 아니다.

- **확인된 맥락 14건.** 팀 프로젝트 '온기'(기부 매칭 서비스)와 그 안의 경험 세 가지(재고 중복 배정을 DB 조건부 UPDATE로 해결해 200건 동시 요청에서 7건 → 0건, N+1 쿼리 개선으로 p95 820ms → 140ms, API 명세 공유 갈등), 개인 프로젝트 '스터디로그'(가입자 37명)와 알림 메일 장애 해결, 학력 2건, 자격증, 기술, 수상, 튜터 경험, 문체 선호("두괄식, '저는' 반복 금지, 과장 금지"), 희망 직무.
- **가상 공고 2개.** 핀테크 백엔드(결제·정산, 동시성 우대)와 커머스 서버(주문·재고, 성능 개선 우대).
- **과제 8건.** 초안 6문항(지원 동기 700자, 기술 문제 해결 1000자, 협업 갈등 700자, 강점 800자, 성능 개선 1000자, 실패 경험 600자)과 첨삭 2건이다. 첨삭 초안에는 과장("완벽하게 해결", "성능이 크게 향상")과 맥락에 없는 기술(Kafka 도입)을 일부러 넣었다.

**조건.** 같은 지시문과 같은 과제로 개인 맥락을 넣지 않은 경우(N)와 넣은 경우(C)를 `gpt-5.4-mini`(공고 추출과 같은 모델, 추론 low)로 한 번씩 생성했다. 지시문은 다음과 같다.

- 제공된 자료(공고, 문항, 개인 맥락, 사용자 초안)에 있는 사실만 쓰고, 없는 경험·수치·기관명·기술은 `[대괄호]` 빈칸으로 남긴다.
- 글자 수 제한을 지키고, 문체 선호가 있으면 따른다.
- 주장마다 근거(맥락 id, 공고, 사용자 초안)를 적는다.

응답은 구조화된 출력(초안: 답변·근거·사용자에게 물을 질문, 첨삭: 고친 답변·구절별 피드백·근거를 확인할 수 없는 초안 내용)으로 받았다.

**평가.**

- **코드 검사.** 답변의 숫자가 맥락·공고·문항·초안에 있는지, 글자 수, 빈칸 수, '저는' 횟수, 첨삭에서 Kafka를 지적하고 뺐는지를 셌다.
- **AI 평가.** `gpt-5.5`가 정답 맥락을 보고 두 답변을 A/B 순서를 무작위로 섞어 평가했다. 사실 정확성·문항 적합성·구체성·문장 품질을 5점으로 매기고, 지어낸 내용을 적고, 제출 준비에 더 쓸 만한 쪽을 골랐다.

**결과.**

| | 맥락 없음 | 맥락 있음 |
| --- | --- | --- |
| 평가자 선호 | 0/8 | 8/8 |
| 평균 점수(사실·적합·구체·문장, 5점) | 3.88 · 2.88 · 1.38 · 2.88 | 4.88 · 4.88 · 4.88 · 5.00 |
| 빈칸 `[ ]` | 37개 | 0개 |
| 근거 없는 숫자 | 2개 | 0개 |
| 평가자가 찾은 지어낸 내용 | 4건 | 1건 |
| 글자 수 초과 | 0건 | 0건 |
| '저는' 사용(문체 선호: 반복 금지) | 6회 | 0회 |
| 첨삭 초안의 맥락에 없는 기술(Kafka) | 고친 답에 남김 | 근거 없음으로 지적하고 뺌 |
| 요청당 입력 토큰·응답 시간 | 약 410 · 3.8~7.9초 | 약 1,130 · 3.6~5.7초 |

맥락이 없으면 기술 문제 해결 문항의 초안이 "[프로젝트명]에서 [기술적으로 어려웠던 문제]를 해결한 경험이 있습니다"처럼 대부분 빈칸이라 쓸 수 없었다. 맥락이 있으면 같은 문항에 "200건 동시 요청 부하 시험에서 중복 배정 건수가 7건에서 0건으로 줄었습니다"처럼 확인된 사실과 수치를 정확히 옮겼다. 첨삭에서는 초안의 과장 표현과 Kafka 등 근거를 확인할 수 없는 내용 다섯 가지를 찾아 빼고, 맥락의 실제 해결 방법으로 고쳐 썼다.

**남은 문제.**

- **표현 과장.** 숫자는 지어내지 않았지만, 200건 동시 요청 시험을 "대용량 요청"으로, 겪지 않은 "트래픽" 문제를 강점으로 썼다. "원인을 단순한 메일 지연으로 봤지만"처럼 맥락에 없는 과정도 덧붙였다. 평가자는 이 중 1건만 잡았고 나머지는 결과를 직접 읽어 찾았다. 숫자는 코드로 맥락과 대조할 수 있지만 표현의 과장은 근거 문장을 사용자에게 보여 확인받아야 한다.
- **근거 표시.** 모든 주장에 맥락 id를 붙여 부풀린 문장도 근거가 있는 것처럼 표시했다. AI가 스스로 붙인 근거는 A1처럼 믿을 수 없다.
- **경험 반복.** 같은 공고의 지원 동기와 기술 문항에 같은 경험(중복 배정 문제)을 반복했다. 같은 지원 건의 다른 문항 답변을 함께 넘겨 경험이 겹치지 않게 해야 한다.
- **질문하지 않음.** 맥락에 없는 회사별 지원 동기를 묻지 않고 일반적인 문장으로 채웠다. 사용자에게 물을 질문은 8건 모두 비어 있었다.

**한계.** 실험용 가상 인물이고, 조건마다 1회 생성했으며, 평가자가 AI다. 쓸수록 사용자가 고치는 양이 줄어드는지와 다른 계정 맥락의 노출은 시험하지 않았다. 다음은 실제 경력을 붙여넣기로 가져와(A2) 본인이 직접 판정하는 시험이다.

**다시 돌리기.** `backend/.env`의 `OPENAI_API_KEY`를 쓴다. 저장소 루트에서 `node _workspace/a3-context/run.mjs`를 실행하면 `results.json`에 생성 결과·검사·평가가 남고 요약이 출력된다. 모델은 `GEN_MODEL`, `JUDGE_MODEL` 환경 변수로 바꾼다. 가상 지원자·공고·과제는 같은 폴더의 `fixtures.json`에 있다.

## A6 직무 적합성 초안의 경험 검색 비교

**목적.** 실제 JaNovel AI가 쓸 모델에서, 확인한 경험을 전부 전달하는 방식과 공고에 관련된 경험을 골라 전달하는 방식의 초안 품질과 원가를 비교한다. 두 방식 모두 채용 공고와 자소서 문항을 받는다.

**환경과 데이터.** 로컬 Node.js 22에서 OpenAI Responses API의 `gpt-6.2-sol`과 추론 설정 `low`를 사용한다. A3 가상 지원자의 경력 기록 12건을 기본 목록으로 사용한다. 확장 목록에는 같은 기술을 공부했거나 팀원의 작업을 검토한 사례 등 헷갈릴 만한 가상 기록 20건을 추가한다. 공고 6개에 공통으로 “지원 직무에 적합하다고 생각하는 이유를 본인의 경험을 근거로 작성해 주세요”를 주고 700자 초안을 요청한다. 결제 정합성, 조회 성능, 메일 장애 대응, API 협업, 기술 교육에는 대표 경험을 미리 지정한다. Kafka 운영 공고에는 직접 경험이 없다.

| 조건 | 생성 모델이 받는 자료 |
| --- | --- |
| 전체 경험 | 공고, 문항, 문체와 글자 수 조건, 확인된 경험 12건 또는 32건 |
| RAG | 같은 공고, 문항, 문체와 글자 수 조건, 의미 검색 상위 경험 4건 |

문서와 검색어는 `text-embedding-3-small`로 임베딩한다. 검색어는 공고 전문과 문항을 합쳐 만들고 코사인 유사도로 상위 4건을 고른다. 목록에 넣은 경험의 원래 순서를 유지한다. 모델, 프롬프트, 글자 수, 응답 스키마는 두 조건에서 같고, 공고와 경험 목록 크기 조합마다 각 조건으로 한 번 생성한다. 공고와 지원자 기록은 가상 데이터다.

**검사 방법.** 검색에서는 미리 지정한 대표 경험이 상위 4건에 남았는지 본다. 초안에서는 사용한 경험과 공고가 연결되는지, 개인 역할과 성과가 원문에 근거하는지, 직접 경험이 없을 때 이를 밝히고 후속 질문을 하는지 본다. 조건 이름을 가린 초안 쌍을 원문과 대조하고, 글자 수·허용된 경험 ID와 API 사용량은 코드로 확인한다. RAG 응답 시간에는 검색어 임베딩과 후보 선택을 포함하며, 경험 등록 시 만드는 임베딩은 별도로 기록한다.

**결과.** 가상 공고 6개와 경험 목록 2종에서 12쌍, 초안 24건을 생성했다. 첫 실행에서 저장한 8건을 재사용하고 나머지 16건을 이어서 실행했다.

| --- | ---: | ---: |
| 대표 경험을 초안에 쓴 경우 | 10/10 | 8/10 |
| 쌍별 정성 검토에서 더 나은 초안 | 3/12 | 0/12 |
| 평균 입력 토큰 | 1,454 | 605 |
| 평균 과금 출력 토큰 | 247 | 226 |
| 모델 호출 지연 중앙값 | 4.64초 | 4.50초 |

- 정성 검토 12쌍 중 9쌍은 품질 차이가 작았다. 대표 경험이 존재한 10개 조합 중 검색 상위 4건에 해당 경험이 남은 경우는 8건이었다. 결제 공고에서는 두 목록 모두에서 같은 실패가 반복됐다. ‘결제’와 가까운 프로젝트 소개나 결제 기술 문서 검토 경험이 먼저 나오고, **조건부 UPDATE로 중복 배정을 해결해 로컬 200건 시험에서 7건을 0건으로 줄인 경험**이 빠졌다. RAG 초안은 매칭 API와 재고 담당을 설명했으나 해결 방법과 검증 수치를 쓸 수 없었다. 32건 목록에서는 조회 성능 사례도 동료 작업을 검토한 경험과 SQL 스터디에 밀려 순위가 3위였지만, 상위 4건에는 남아 초안에서 쓰였다.
- Kafka 운영 필수 공고에서는 양쪽 모두 직접 운영 경험이 없다고 밝히고 확인 질문을 했다. 확장 목록의 전체 경험 초안은 로컬 Kafka 학습 범위와 실제 메일 API 장애 격리 경험을 함께 설명했다. RAG 초안은 검색에서 장애 격리 경험이 빠져 로컬 학습과 경험 부재만 적었다. 기술 교육 초안 일부는 질문 정리·공유를 ‘학습 자료로 공유’라고 표현했다. 출처 ID의 유효성 검사만으로는 이처럼 원문보다 의미가 커지는 표현을 탐지하기 어렵다.

**해석과 한계.** 자동으로 초안에 쓸 경험을 맡기는 두 조건에서는 전체 경험을 전달했을 때 더 적합한 경험을 썼다. 같은 가상 지원자와 6개 공고를 두 목록 크기에서 반복했고, 조건당 한 번 생성했으며, 초안의 정성 판정은 Codex 한 번의 검토다. 비교 요청은 한 번에 최대 두 쌍을 처리했고 검색어 임베딩 시간을 재사용했다. 사용자가 소재를 고르는 흐름과 실제 제출 선호는 이번 비교에서 측정하지 않았다.

**후속 제품 검증.** 검색 결과를 소재 후보로 보여주고, 사용자가 선택한 경험을 공고·문항과 함께 전달한다. 추천에서 빠진 경험은 전체 목록에서 직접 고를 수 있다. 실제 사용자가 소재를 고르는 시간과 검색 목록 밖에서 고른 경우를 기록한다. 검색 품질을 다시 평가할 때는 공고에 필요한 행동과 제약을 검색어로 쓰는 방식, 키워드와 의미 검색을 결합하는 방식도 같은 표본에서 비교한다. 서비스 연결 전에는 계정 간 검색 격리, 확인 대기 경험 제외, 경험 수정·삭제 뒤 기존 검색 결과가 다시 쓰이지 않는지를 확인한다. [문항에 쓸 경험 선택](05-local-agent-chat-review.md#문항에-쓸-경험-선택)

### 후속 pgvector 저장 실험

격리된 PostgreSQL 19 임시 컨테이너에 pgvector 0.8.7을 올렸다. 가상 경험으로 1,536차원 벡터를 저장해 사용자별 코사인 거리 정렬, 원문 수정 뒤 이전 벡터 제외, 원문 삭제 시 벡터 연쇄 삭제를 확인했다. 별도로 실제 OpenAI 임베딩을 사용한 가상 경험 6건의 확인에서는 중복 배정 해결 경험이 추천 상위 4건에 들지 않았다. 같은 경험은 전체 목록에서 조회됐다. 저장 실험은 `bash _workspace/pgvector-storage-experiment/run.sh`로 재현할 수 있다. 외부 모델 호출 없이 임시 DB에서만 실행된다. 제품 코드와 개발 DB에 pgvector를 도입할지는 검색 품질 검증 뒤 결정한다.

## B1 Claude Code Channels

**방법.** 중계 서버, 웹 채팅 페이지, Claude Code용 JaNovel 채널(stdio MCP 서버)을 만들었다. 채널은 중계 서버를 롱폴링해 등록된 계정의 메시지만 세션에 넣고 `reply` 도구로 답을 돌려준다. 권한 승인 중계는 선언하지 않았다. SDK 클라이언트로 한 사전 점검 8개 항목을 통과한 뒤 실제 Claude Code 대화형 세션을 `--dangerously-load-development-channels`로 띄워 시험했다.

**결과.** 웹에서 보낸 첨삭 요청이 세션에 들어가고 약 25초 뒤 `reply`로 웹에 답이 표시됐다. 등록하지 않은 보낸 사람의 메시지는 채널에서 버렸다. 미끼 파일 읽기와 파일 생성 요청은 거부했지만, 설정이 막은 것이 아니라 Claude가 판단해 거부한 것이다. 거부 답은 터미널에만 쓰고 웹으로 보내지 않아, 거부도 `reply`로 보내게 채널 안내문을 고쳐야 한다. 응답은 스트리밍되지 않고 완성된 답 한 번으로 온다. 개발용 플래그의 경고 화면을 통과해야 하고 터미널을 열어 둬야 한다. 사용자 설정에 파일 읽기·셸이 허용된 상태에서 전용 폴더의 거부 규칙이 막는지는 다시 시험한다.

## B2 Codex app-server

**방법.** 중계 서버의 연결 관리자가 `codex app-server`를 stdio로 실행하고 읽기 전용 샌드박스, 승인 거부, 임시 스레드로 대화를 시작한다. 시험 스크립트가 첨삭 요청, 작업 폴더 밖 미끼 파일 읽기 요청, 파일 쓰기 요청을 차례로 보낸다.

**결과.** 기존 CLI 로그인으로 초기화하고 스레드를 만드는 것까지 확인했다. 대화는 Codex 사용 한도에 걸려 실행되지 않아, 응답 스트리밍과 미끼 파일 유출 여부는 확인하지 않았다. 설치된 Codex 0.171의 읽기 전용 샌드박스에는 읽기 범위 옵션이 없어, 재시험에서는 권한 프로필로 폴더 밖 읽기를 막는다.

## 중단한 웹 MCP 첨삭 실험

ChatGPT·Claude 웹에서 JaNovel MCP로 첨삭하는 경로를 가짜 검토 요청 1건으로 시험했다. 시험 서버 점검(실험 0), Claude Pro 웹(실험 1), ChatGPT Plus 웹 개발자 모드(실험 2), 대화 안 후보 카드(실험 1-1)가 모두 동작했지만, 대화가 JaNovel 밖에 남아 2026-11-27에 이 경로를 쓰지 않기로 했다. 다음 관찰은 다른 경로의 설계에 쓴다.

- 두 서비스 모두 쓰기 도구를 승인 창 없이 실행했다. 그래서 후보 저장은 원본을 바꾸지 않고 채택은 사용자 동작으로만 하는 분리를 유지한다.
- ChatGPT는 JaNovel 자료에 없는 사용자 경력·수치를 기억에서 가져와 후보에 넣었고 확인 필요 표시는 대부분 빠졌다. 그래서 근거 출처를 표시하고 확인되지 않은 사실은 맥락에 올리지 않는다.
- Claude는 이전 대화와 같은 중복 방지 키를 다시 만들어 새 후보 대신 이전 후보가 반환됐다. 그래서 같은 키에 다른 내용이 오면 오류로 돌린다.
- ChatGPT는 위젯 카드 아래에 자체 요약 카드와 표를 다시 만들어 같은 정보가 반복됐다.
