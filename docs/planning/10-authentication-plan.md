# 인증과 계정 기획

2026-11-26 정리 · 설계 전

## 현재 상태

서버 인증은 아직 없다. 지원 건과 내 공통 자소서 API는 브라우저 미리보기 프로필이 가진 접근 키(`Authorization: Bearer <소문자 16진수 64자>`)로 사용자를 구분한다. 키를 아는 사람은 누구나 그 데이터에 접근하므로 공개 전에 교체한다. [미리보기 사용자 처리](../../backend/src/main/java/com/janovel/domain/user/app/PreviewUsers.java)

스키마에는 `users`(이메일, 이름, 비밀번호 해시, 시간대)와 `oauth_accounts`(제공자, 제공자 사용자 ID)가 있다. 프론트의 이메일 로그인·가입·비밀번호 재설정·Google 로그인은 로컬 화면 시연이다. 공고 추출과 문항 공유 API는 로그인 없이 열려 있다. [제품 기획](01-product-plan.md)

## 목표와 범위

1. 사용자가 로그인하고 본인의 지원 건·작성·일정·면접 자료만 조회하고 수정한다.
2. 모델 호출처럼 비용이 드는 API는 로그인한 사용자만 사용하고 사용자별로 호출 횟수를 제한한다.
3. AI 채팅 1차의 ChatGPT 계정 로그인은 선정된 상업 파트너 대상의 제한 시범이라 신청과 승인이 필요하다. 서비스의 유일한 로그인으로 삼지 않고, 서비스 계정에 ChatGPT 인증을 연결해 쓴다. 계정 식별은 이메일이 아니라 발급자, client ID, `sub`로 한다. [AI 연결 검토](05-local-agent-chat-review.md)

| 로컬 개발 | 개발용 로그인을 둘지, 접근 키를 `local` 프로필에서만 허용할지 | 개발 편의와 배포 서버에 우회 경로가 남지 않는 것을 함께 본다. |

## JWT 설계 방향

아래는 후보이며 구현 전에 확정한다.

- **서명.** 비대칭 키(RS256 또는 ES256)로 서명하고 공개 키를 JWKS 주소로 제공한다. 서비스가 나뉘어도 다른 서비스가 비밀 키 없이 검증한다.
- **액세스 토큰.** 수명은 10~15분이다. `sub`에는 우리 서비스의 사용자 ID를 넣고 `iss`, `aud`, `exp`, `jti`를 둔다. 이메일 같은 개인 정보는 넣지 않는다. 프론트는 메모리에만 보관하고 브라우저 저장소에 두지 않는다.
- **리프레시 토큰.** `HttpOnly`·`Secure`·`SameSite` 쿠키로 전달하고 갱신할 때마다 새 토큰으로 바꾼다. 서버에는 해시로 저장해 로그아웃이나 유출 때 폐기한다.
- **즉시 차단.** 액세스 토큰을 짧게 유지하고 리프레시 토큰을 폐기해서 처리한다. 즉시 차단이 꼭 필요한 기능이 생기면 `jti` 차단 목록을 둔다.
- **구현.** 검증은 Spring Security의 리소스 서버로 하고, 발급은 직접 구현할지 Spring Authorization Server를 쓸지 비교한다.
- **서비스를 나눌 때.** 발급은 인증을 맡은 한 곳이 하고 나머지는 검증만 한다.

## 적용 원칙

- 서비스 메서드는 항상 `userId`를 받고 사용자별로 걸러서 조회한다. 사용자는 컨트롤러의 한 지점에서만 정하고 요청이 보낸 사용자 번호는 믿지 않는다. 전환할 때 이 지점과 접근 키 파라미터만 바꾼다.
- 다른 사용자의 자료는 없는 자료와 같은 `404`로 응답한다.
- 인증을 켜면 모든 경로가 기본으로 인증을 요구하고 로그인·상태 확인 같은 공개 경로만 허용한다.
- 문항 공유는 로그인한 사용자만 입력하고 제보를 검토한 뒤 공통 문항에 반영한다.
- 접근 키와 `essay-template+...@janovel.invalid` 임시 사용자는 전환할 때 제거한다. 개발 중 데이터는 옮기지 않고 비운다.

## 진행 순서

1. 프론트를 서버에 연결하기 전에 위 결정 항목을 정한다.
2. 보안 설정을 적용한다. 기본은 전체 인증이며 기존 컨트롤러 테스트의 인증 방식을 바꾼다.
3. 프론트의 로그인 화면을 서버 로그인에 연결하고 접근 키를 제거한다.
4. 호출 횟수 제한과 메모리 한도를 갖춘다. [개발 순서](01-product-plan.md#개발-순서와-완료-확인)

## 검증

- 다른 사용자의 지원 건 조회·수정이 `404`로 거부되는지 확인한다.
- 로그아웃이나 세션 만료 뒤 `401`을 반환하고, 로그인 없이 모델 호출 API를 쓸 수 없는지 확인한다.
- 허용한 프론트 주소만 CORS와 CSRF 검사를 통과하는지 확인한다.
- 소셜 로그인 취소·실패, 여러 기기의 동시 로그인, 로그인 뒤 원래 화면으로 돌아가는 흐름을 확인한다.

## 미결

로그인 방식과 상태 유지 방식, 이메일 확인 필요 여부, 탈퇴와 데이터 삭제 정책(자소서 본문 포함), 관리자 계정 필요 여부는 정하지 않았다.
