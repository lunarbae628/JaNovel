# 공고 가져오기 동시 처리 계획과 검증

이 문서는 로컬 OCR 경로를 사용한 당시 기획과 검증 기록이다. [현재 공고 가져오기](08-posting-structured-import.md)

## 계획

목표는 로컬 환경에서 브라우저와 OCR 처리 한도를 늘렸을 때 성공 건수가 늘어나는지 확인하고, 응답 시간이 얼마나 달라지는지 비교하는 것이다. [공고 추출 설계](06-posting-ocr-plan.md)

1. Chromium 처리 슬롯을 `1`개와 `2`개로 실행할 수 있게 한다. 슬롯마다 전용 스레드와 Chromium 인스턴스를 사용하고, 개별 요청은 새 브라우저 컨텍스트에서 실행한다.
2. OCR 처리 슬롯의 프로세스 수와 프로세스당 CPU 스레드 수를 지정하게 한다. 총 스레드를 네 개로 맞춰 `1 × 4`와 `2 × 2`를 비교한다.
3. 동일한 요청을 동시에 보내고, 허용한 요청의 소요 시간과 `200`·`503`·`504` 건수를 기록한다. 준비 시간과 예열 이후 요청은 따로 기록하고, 브라우저와 OCR 부하 시험은 순차 실행한다.
4. 일반 HTTP 빠른 경로, 공개 주소 제한, 슬롯 초과 시 즉시 `503`, OCR 시간 초과 후 재준비를 유지한다. 단독 응답 시간과 동시 성공 건수를 함께 보고 기본값을 정한다.

## 검증 결과

2026-11-25, Apple M4 Pro 14코어·24 GiB, Java 21·로컬 Chrome, Python 3.10·CPU PaddleOCR에서 확인했다. 브라우저와 OCR은 각각 따로 측정했다. 동시에 보낼 요청은 시작 장벽으로 맞췄고 준비 요청은 응답 시간 중앙값에서 제외했다.

### 브라우저

실제 NHN 공고의 렌더링 경로를 `PostingBrowserClient.render`로 호출했다. 공고 본문에서 `주요 업무`와 `모니터링`이 확인돼야 성공으로 셌다. 슬롯별 예열 후 단독 요청 세 건과 동시 2건을 세 차례 보냈다.

| 구성 | 단독 응답 중앙값 | 동시 요청 결과 | 동시 요청 중 성공 응답 중앙값 | 피크 RSS 합계 |
| --- | --- | --- | --- | --- |
| 브라우저 1개 | 0.513초 | `200` 3건, `503` 3건 | 0.514초 | 1,063 MiB |
| 브라우저 2개 | 0.508초 | `200` 6건 | 0.536초 | 1,939 MiB |

RSS는 Java 프로세스와 자식 프로세스를 200ms 간격으로 합산한 값이다. 공유 메모리가 중복될 수 있고, 2개 구성의 피크에는 본문 캡처 한 건이 포함됐다. 외부 페이지의 응답도 포함한 소규모 실측이다.

**브라우저 기본값은 2개**로 적용했다. 첫 번째 워커가 사용 중일 때 두 번째를 선택하고 각 워커가 첫 호출에서 브라우저를 띄운다. 메모리 여유가 적으면 `JANOVEL_POSTINGS_BROWSER_WORKERS=1`로 운용할 수 있다. HTML만으로 끝나는 요청은 기존 HTTP 빠른 경로를 사용한다.

최종 기본 설정의 Java 서버를 띄운 직후 `POST /api/postings/import`에 NHN 링크 세 건과 원티드 링크 한 건을 동시에 보냈다. NHN 두 건은 본문을 포함한 `200`을 각각 3.20초에 반환했고, 나머지 한 건은 0.15초에 `503 POSTING_IMPORT_BUSY`를 반환했다. 원티드는 같은 요청 묶음에서 0.26초에 본문과 `200`을 반환했다.

### OCR

`POST /internal/ocr`에 한국어 첨부 이미지(900×320)와 같은 NHN 공고의 상세 캡처(806×2570)를 PNG로 보냈다. 각 설정과 입력을 예열하고 단독 요청 세 건과 동시 2건을 세 차례 보냈다. 단독 요청은 네 조합 모두 `200` 3건이었다. `200`의 본문은 설정을 바꿔도 같은 텍스트였고, 주요 업무 등 예상 텍스트도 확인했다.

| 입력 | 워커 × CPU 스레드 | 단독 중앙값 | 동시 요청 결과 | 동시 요청 중 성공 응답 중앙값 |
| --- | --- | --- | --- | --- |
| 첨부 이미지 | `1 × 4` | 0.511초 | `200` 3건, `503` 3건 | 0.512초 |
| 첨부 이미지 | `2 × 2` | 0.518초 | `200` 6건 | 0.549초 |
| NHN 캡처 | `1 × 4` | 9.069초 | `200` 3건, `503` 3건 | 9.130초 |
| NHN 캡처 | `2 × 2` | 9.117초 | `200` 6건 | 9.593초 |

OCR 서비스와 자식 프로세스의 피크 RSS 합계는 `1 × 4`에서 1,509 MiB, `2 × 2`에서 2,703 MiB였다. `2 × 2`에서 NHN 동시 처리의 가장 느린 성공 응답은 9.780초였다. 측정한 조합에서는 `504`가 없었다. 별도 동작 검증에서는 워커 둘이 사용 중일 때 세 번째 요청의 `503`, 한 워커의 시간 초과·종료 뒤 재기동, 다른 워커의 계속 처리를 확인했다.

**OCR 기본값은 `1 × 4`**다. 워커 두 개는 같은 시간대에 두 건을 처리하지만 메모리 여유가 더 필요하고, 긴 캡처는 10초 작업 제한에 가까웠다. 메모리가 충분한 머신에서는 `server.py --workers 2 --cpu-threads 2`로 실행할 수 있다. [OCR 실행 가이드](../../backend/ocr/README.md)

### 측정 범위

이 결과는 한 대의 개발 머신에서 브라우저와 OCR을 각각 따로 실행한 값이다. 두 작업을 동시에 요청하는 혼합 부하와 배포 서버 환경은 별도로 측정해야 한다. 현재 슬롯이 차면 바로 `503`을 반환한다. 계속 사용하는 사용자가 늘면 실제 부하에서 실패율을 확인한 뒤 대기 처리를 도입할지 판단한다.

## 가입자 100명 기준 배포 계획

요청 비율과 목표 응답 시간은 출시 전 검증할 가정이다. 작업 접수·조회는 단일 Java 인스턴스용 메모리 대기열을 사용한다. 서버 재시작 또는 조회 기간 만료 후 작업을 다시 요청할 수 있다.

### 사용량 가정

가입자 100명이 하루 2건씩 공고를 등록한다고 가정한다. 하루 등록 시도 200건 중 링크 90%, 이미지 첨부 10%다. 링크의 25%는 브라우저로 텍스트를 읽고, 링크의 10%는 사용자가 OCR로 재시도한다고 가정한다.

| 항목 | 하루 예상 건수 |
| --- | --- |
| 링크 가져오기 | 180건 |
| 링크 텍스트를 위한 브라우저 렌더링 | 45건 |
| OCR 재시도를 위한 브라우저 캡처 | 18건 |
| OCR 전체 | 38건 (이미지 첨부 20건, 링크 재시도 18건) |

집중 부하는 **5분에 등록 20건**, 순간 부하는 **OCR 5건 동시 도착**으로 검증한다. 5분 등록 시나리오에는 링크 18건, 이미지 첨부 2건, 링크 OCR 재시도 2건을 넣는다. 가입자 100명이 동시에 OCR을 요청하는 상황은 별도 용량 목표로 본다.

### 처리와 대기

- **일반 링크 가져오기**는 HTTP·Jsoup으로 본문을 읽고, 필요한 경우에만 브라우저로 렌더링한 뒤 동기 응답한다. 준비된 브라우저 환경에서 결과까지 걸리는 시간의 95번째 백분위(`p95`) 목표는 3초다.
- **OCR**은 Java가 작업을 접수한 뒤 별도 서버에서 처리한다. 링크 재시도는 브라우저 캡처 시간도 포함한다. 화면은 결과가 올 때까지 로딩 상태를 유지하고, 완료 후 확인·수정·등록으로 진행한다. 작업 상태를 조회할 때는 약 1~2초 간격을 둔다. 같은 등록 화면에서 진행 중인 OCR 요청은 한 건으로 제한한다.
- OCR의 **평상시 목표는 클릭부터 결과 표시까지 `p95` 10초**, **대기 상한은 25초**다. 처리 중인 작업 외에 최대 3건을 대기 후보로 받는다. 이미 대기 중인 작업과 단계별 소요 시간을 계산해 상한 내 완료가 어려우면 접수 전에 `503`으로 응답한다. 접수한 작업이 상한을 넘기면 대기 상태를 종료하고 원문과 함께 재시도 또는 직접 입력을 제공한다.

### 배포 서버와 채택 기준

별도 OCR 서버에서 모델을 미리 올린 워커 **2개**와 **3개**를 차례로 확인한다. 첫 목표는 긴 캡처의 OCR 처리 `p95` 7초 이내다. 한 장에 7초씩 걸린다고 단순 계산하면, 동시 5건에서 워커 2개는 마지막 결과까지 추론만 21초, 3개는 14초가 걸린다. 여기에 업로드·캡처·전송·결과 조회 시간이 더해진다. 실측으로 목표를 만족한 가장 작은 구성을 채택한다. [대기 시간 기준으로 작업 용량을 잡는 예시](https://docs.aws.amazon.com/autoscaling/ec2/userguide/as-using-sqs-queue.html)

1. 배포 후보 서버에서 짧은 첨부 이미지와 긴 한국어 공고 캡처를 사용해 5분 혼합 부하를 반복한다. 정상 부하의 OCR 요청을 100건 이상 모아 첫 시도와 재시도 각각의 성공률, 결과 표시 시간, 캡처·대기·추론 시간, 메모리·CPU를 기록한다.
2. **5건 동시 도착**을 별도 시험한다. PNG 5건을 보낸 경우와 링크 캡처 3건·첨부 2건을 보낸 경우 모두에서 `5/5`건이 25초 안에 완료되는지 확인한다. 초과 요청에서는 대기열 상한과 실패 안내가 동작하는지 확인한다.
3. 정상 부하에서 링크와 OCR의 `p95` 목표를 충족하고, 입력이 정상인 OCR 처리의 성공률이 99% 이상이면 시작 구성으로 채택한다. 한 장 처리 시간이 목표를 넘으면 모델 설정이나 서버 자원을 조정한다. 한 장은 빠르고 대기가 길면 워커 수를 조정한다.

### 구현 및 기능 검증

1. OCR 요청 두 종류의 `202` 접수와 작업 조회 API를 구현한다. OCR 실행 수는 서버의 워커 수와 맞추고 대기열은 최대 3건이다. 작업 처리 한도는 접수 후 23초, 프론트 대기는 요청 시작부터 최대 25초다. 배포 실측 전의 접수 추정치는 첨부 8초, 링크 재시도 12초다.
2. 확인 화면은 처리 중 입력과 등록을 잠그고 완료·실패 뒤 다시 열어 준다. 일반 링크 가져오기 `200`은 바로 표시한다.
3. 정상 수락·조회·완료, 실패 전달, 한도 초과, 기존 링크 응답과 화면 상태를 검증한다. 처리량과 응답 시간 목표는 배포 서버에서 별도 검증할 항목이다. [로컬 API 명세](../api/README.md#공고-이미지-가져오기)

작업 상태 조회의 완료·실패 응답은 최대 2분간 메모리에 남긴다. 응답 추정치와 대기열 길이가 허용 범위를 넘으면 즉시 거절하고, 접수한 작업은 같은 마감 시간을 브라우저 슬롯 대기와 OCR 결과 수신에 적용한다.

기능 검증에서 테스트용 OCR에 연결한 실제 Java API로 이미지 첨부와 링크 캡처를 접수해 완료 결과를 조회했다. 접수·조회 httpYac 예제, 실행 및 대기 중 추가 요청의 `503`, 없는 작업의 `404`, OCR 연결 중단 뒤 `FAILED`, 기존 링크의 `200`을 확인했다. 프론트는 Chromium에서 대기·처리 중 입력과 저장이 잠기고 완료·실패 뒤 원문과 입력값이 보존되는 것을 확인했다.
