# 공고 링크와 이미지의 로컬 추출

상태 `구현됨`

공개 공고 링크와 첨부 이미지에서 본문을 읽어 기존 등록 확인 화면에 채운다. 사람인에서 확인한 사례는 HTTP `200`으로 페이지 제목과 메뉴를 반환했지만, 회사명·마감일과 실제 공고 본문은 빠져 있었다. 성공 조건을 공고 본문을 확보한 경우로 잡는다. [현재 공고 가져오기 서비스](../../backend/src/main/java/com/janovel/domain/application/app/PostingImportService.java)

## 두 서비스의 역할

| 서비스 | 담당 |
| --- | --- |
| Java 백엔드 | 링크와 첨부 이미지 검증, HTML 파싱, Playwright로 렌더링·캡처, OCR 호출, 공고 필드와 API 오류 응답 조립 |
| Python OCR | 이미지의 형식과 크기 확인, PaddleOCR로 텍스트 추출, 읽힌 순서대로 줄바꿈을 포함한 본문 반환 |

한 대에서 두 서비스를 실행한다. 첫 버전은 Java가 OCR을 동기 HTTP로 한 번 호출한다. 같은 머신에서 직접 실행할 때 OCR은 루프백 주소에 바인딩한다. Compose를 사용하면 내부 네트워크에서 서비스 이름으로 연결하고 OCR 포트는 호스트에 공개하지 않는다. 비동기 작업 방식은 대기 후 결과를 받을 수 있지만 작업 상태와 결과 보관이 필요하므로, 실제 요청 시간과 동시 사용량을 측정한 뒤 판단한다. [Playwright 요소 캡처](https://playwright.dev/java/docs/screenshots) · [PaddleOCR 한국어 모델](https://www.paddleocr.ai/main/en/version3.x/algorithm/PP-OCRv5/PP-OCRv5_multi_languages.html)

## 입력에서 확인 화면까지

1. **링크**는 기존 HTTP·Jsoup 파싱을 먼저 시도한다. `JobPosting.description`이나 본문 영역에서 업무·자격·모집 안내를 읽으면 바로 확인 화면으로 보낸다. 제목, 메뉴나 추천 공고만 읽히면 Playwright에서 공개 페이지를 렌더링해 실제 본문 텍스트를 읽는다. 읽은 결과가 없더라도 원문 링크와 수동 입력 화면을 제공한다.
2. **이미지로 다시 가져오기**를 사용자가 누르면 링크의 공고 영역을 캡처해 OCR에 보낸다. 원문 링크와 사용자가 편집한 내용은 계속 보존한다. **첨부 이미지**는 Java가 파일을 검증한 뒤 같은 OCR에 전달한다. 지원 형식은 JPEG·PNG·WebP, 상한은 10 MiB 및 디코딩 시 2,000만 픽셀이다.
3. Java는 확보한 본문과 확인 가능한 회사·직무·마감일을 반환한다. 필드 근거가 부족하면 기존 응답 규칙에 따라 빈 문자열을 사용한다. 마감일은 공고에 날짜가 명시된 경우에만 채운다.

브라우저 프로세스는 재사용하고 요청마다 격리된 컨텍스트를 연다. 모든 브라우저 연결은 Java의 로컬 프록시를 거치며, 프록시가 실제 연결 주소를 검증한 뒤 검증한 IP에 연결한다. 사설망·루프백·링크 로컬과 기본 포트 밖의 연결은 차단한다. 텍스트를 읽을 때는 이미지·동영상·폰트 로딩을 줄이고 캡처에서는 이미지와 폰트를 허용한다. 로그인이 필요하거나 접근이 차단된 공고는 이미지 첨부 또는 수동 입력으로 이어진다.

## API 명세

| 호출 | 요청 | 응답 |
| --- | --- | --- |
| `POST /api/postings/import` | 기존 JSON `{"url":"https://…"}` | `200`, 기존 `company`, `role`, `deadline`, `sourceText` |
| `POST /api/postings/import/ocr` | 사용자가 OCR 재시도를 눌렀을 때 같은 JSON 본문 | `202`, 작업 ID와 상태 조회 경로 |
| `POST /api/postings/import-image` | `multipart/form-data`의 필수 `image` 파일 한 개 | `202`, 작업 ID와 상태 조회 경로 |
| `GET /api/postings/import-jobs/{jobId}` | 접수할 때 받은 작업 ID | `200`, 작업 상태와 완료 결과 또는 실패 사유 |
| `POST /internal/ocr` | Java가 이미지 바이트를 본문으로 전송. `Content-Type`은 이미지 형식, `X-Request-Id`는 두 서비스의 로그를 연결하는 요청 ID | `200`, `{"text":"읽을 수 있는 본문"}`. 글자가 없으면 `text`는 빈 문자열 |

Java가 내부 요청의 결과를 공통 오류 본문인 `status`, `message`, `error`로 매핑한다. OCR 내부 오류는 `error` 한 필드로 사유를 전달한다. 두 서비스는 요청 ID, 걸린 시간과 오류 코드만 남기고 이미지와 본문은 요청 처리 중에만 사용한다.

## 타임아웃과 장애 대응

| 구간 | 시작값 | 동작 |
| --- | --- | --- |
| 프론트 대기 | 링크 30초, OCR 25초 | OCR은 접수부터 조회까지 같은 예산을 쓴다. 화면을 떠나면 결과 조회를 취소한다. |
| Java 처리 | 링크 최대 14초, OCR 작업 최대 23초 | OCR 작업의 한도는 접수 시점부터 대기·캡처·추론을 포함한다. |
| 요청 본문 | 파일 최대 10 MiB, multipart 요청 최대 11 MiB | Java가 업로드 크기를 제한하고, 이미지 디코딩은 OCR 처리 슬롯을 확보한 뒤 진행한다. |
| HTML 가져오기 | 최대 6초 | 접속·리다이렉트·본문 읽기까지 같은 한도를 쓴다. |
| 브라우저 렌더링과 캡처 | 최대 8초 | 브라우저 진입부터 계산하고, 성공·실패 모두 요청별 브라우저 컨텍스트를 닫는다. |
| Java → OCR | 최대 12초 | 접속은 최대 1초다. 요청 전송부터 결과를 읽을 때까지 12초 안에 마친다. |
| OCR 디코딩과 추론 | 최대 10초 | 준비된 작업 프로세스 한 개를 쓴다. 크기와 픽셀 수를 확인하고 디코딩과 추론을 마친다. 한도를 넘으면 해당 프로세스를 종료하고 새 작업 프로세스에서 모델을 다시 준비한다. |

시작 한도는 개발 머신에서 링크·캡처·첨부 경로의 응답을 확인하며 잡았다. 브라우저는 기본 두 건까지 동시에 처리하고, OCR은 기본 한 건에 CPU 스레드 설정 네 개를 사용한다. OCR은 두 건·프로세스당 스레드 두 개로도 실행할 수 있다. 각 슬롯이 이미 사용 중이면 `503`을 반환한다. Playwright는 워커별 전용 스레드에서 호출하고 요청별 브라우저 컨텍스트를 사용한다. [동시 처리 계획과 검증](07-posting-concurrency.md) · [Playwright Java 스레드 가이드](https://playwright.dev/java/docs/multithreading)

OCR은 모델을 로드한 작업 프로세스가 정상일 때 `GET /readyz`에서 `200`을 반환한다. 초기화하거나 장애 후 다시 로드하는 동안은 `503`을 반환한다. `POST /internal/ocr`는 이미 추론 중이면 `503 OCR_BUSY`, 준비가 안 됐으면 `503 OCR_NOT_READY`를 반환한다. Java는 요청 결과에서 OCR 응답과 연결 오류를 처리하며 OCR 호출은 요청당 한 번이다. 호출자가 먼저 연결을 끊더라도 이미 시작된 OCR 작업은 자체 한도 내에서 끝낸다. 작업 완료 또는 시간 초과에 따른 프로세스 종료를 확인한 뒤 슬롯을 반환한다. 사용자는 원문을 유지한 채 재시도하거나 직접 입력할 수 있다.

| 상황 | Java 공개 API 응답 | 화면 |
| --- | --- | --- |
| 잘못된 URL, 파일 누락 또는 디코딩 불가 | `400 INVALID_POSTING_URL`, `400 INVALID_REQUEST`, `400 POSTING_INVALID_IMAGE` | 입력값을 유지하고 해당 입력을 고치도록 안내 |
| 파일 크기나 픽셀 수 초과, 지원 형식 아님 | `413 POSTING_IMAGE_TOO_LARGE` 또는 `415 UNSUPPORTED_POSTING_IMAGE` | 더 작은 이미지 또는 지원 형식으로 다시 첨부하도록 안내 |
| 이미지에서 텍스트를 찾지 못함 | `422 POSTING_TEXT_NOT_FOUND` | 확보한 원문과 함께 수동 입력 화면 표시 |
| 링크 본문 없음, 응답 오류 또는 접근 제한 | `502 POSTING_UNREADABLE` | 원문 링크를 유지하고 이미지 첨부나 수동 입력 안내 |
| OCR이 `500`을 반환하거나 성공 응답이 계약과 다름 | `502 POSTING_OCR_FAILED` | 입력을 보존하고 재시도 또는 수동 입력 안내 |
| OCR에 연결할 수 없거나 아직 초기화 중 | `503 POSTING_OCR_UNAVAILABLE` | 잠시 후 재시도 또는 수동 입력 안내 |
| 브라우저 또는 OCR이 처리 중 | `503 POSTING_IMPORT_BUSY` | 잠시 후 재시도 또는 수동 입력 안내 |
| 필요한 HTML·브라우저·OCR 단계 또는 전체 추출 시간 초과 | `504 POSTING_TIMEOUT` | 입력을 보존하고 재시도 또는 수동 입력 안내 |

이미지 내용 오류는 OCR에서도 `400`·`413`·`415`로 구분하고, 추론 제한 시간 초과는 `504`로 응답한다. Java는 각 원인을 확인 화면에 표시할 공통 오류 메시지로 변환한다. [HTTP 오류 상태 정의](https://www.rfc-editor.org/rfc/rfc9110#section-15.6)

## 실제 요청 확인

1. HTML에서 본문이 읽히는 원티드와 렌더링 뒤 본문이 나타나는 NHN을 대조한다. 본문이 이미지나 혼합형인 공고는 사용자가 OCR 재시도를 눌러 확인한다.
2. 첨부 이미지, OCR 중지·초기화 중·동시 호출·느린 추론과 잘못된 파일을 확인한다. 프론트의 입력값 보존과 OCR 재준비 후 새 요청 처리도 확인한다. [httpYac 요청 예제](../../backend/http/posting-ocr.http)
3. 임의 링크의 브라우저 경로를 공유 환경에 배포하기 전에 리다이렉트와 하위 리소스의 사설 IP 차단을 확인한다.

## 구현과 검증 순서

1. 컨트롤러에 링크 재시도와 이미지 첨부 계약을 추가한다. 원티드 HTML과 NHN 렌더링 결과를 `.http`로 대조한다.
2. Java의 브라우저·OCR 클라이언트를 연결하고 Python OCR을 별도 프로세스로 띄운다. 공개 주소 검사, OCR 읽기, 연결 오류와 시간 제한을 검증한다.
3. 확인 화면에서 OCR 재시도와 이미지 첨부를 연결한다. 예전에 입력한 값과 원문이 보존되는지 확인하고 백엔드 테스트와 프론트 빌드를 실행한다.
