# Docsa 기반 신규 취업 준비 서비스 기획

작성일 2026-10-15 · 수정일 2026-11-13 · v1.9 · 합의한 제품 범위의 확정본 · 구현·실사용 검증 전

## 1. 기획의 결론

자소서를 여러 번 고치고 여러 회사에 지원하는 과정에서, 무엇을 왜 바꿨고 실제로 무엇을 제출했는지 남기는 서비스다. 공고와 문항, 수정 이력, 제출본을 한 지원 건에 묶고 면접 준비에서 다시 꺼내 쓴다.

개인용으로 먼저 만들어 검증할 가치는 있다. 다만 버전관리와 취업 준비 통합 기능 자체는 경쟁 서비스에도 있으므로 사업 경쟁력은 아직 입증되지 않았다. 첫 검증은 **무엇이 바뀌었는지 한눈에 확인하는 경험**과 AI 피드백이 기존 GPT·문서·캘린더 조합보다 실제로 도움이 되는지에 둔다. 경쟁 근거와 반론은 [별도 검토 문서](02-critical-review.md)에 정리했다.

### 2026-11-13 작성안 구조 변경

사용자 승인: 같은 문항에 서로 다른 주제를 시도할 수 있도록 독립된 작성안을 둔다. 각 작성안 안에서 스냅샷으로 수정 과정을 기록하며, 같은 작성안이나 다른 작성안의 스냅샷·작성 중 본문을 자유롭게 비교한다. 두 주제는 구절·전체 본문을 선택하고 직접 다듬어 새 작성안으로 합칠 수 있다. 원본 두 작성안은 보존하고 조합 당시의 참고 본문을 기록한다. 이 결정은 아래 과거 분기·병합 설계보다 우선하며 현재 프론트에 적용한다. 기존 데이터와 제출본은 유지한다.

### 2026-11-13 면접·개인 할 일 결정

면접은 **예상 질문 정리 페이지**와 **Voice API 기반 음성 모의면접 모드**를 분리한다. 모의면접에 텍스트 답변 입력을 먼저 구현하는 단계를 두지 않는다. 음성 질문·답변·꼬리 질문과 종료 후 전사·피드백 기록을 설계하며, 실제 제공자·연결 방식·비용은 구현 전 검증한다. 전사는 읽기용 기록이며 키보드 답변 입력을 뜻하지 않는다. 캘린더는 지원 일정 외에도 회사에 연결되지 않은 개인 할 일을 추가하고, 날짜·선택 시간·완료 여부를 관리한다. 개인 할 일 완료가 지원 단계·제출 여부를 변경하지 않는다. 공통 경험·자료 보관함은 사용자가 제외했다.

## 3. 누구의 어떤 문제를 푸는가

첫 사용자는 Java/Spring Boot 중심으로 지원하는 본인이다. 초기 검증 대상으로는 여러 기업의 자소서 문항을 작성하고 GPT 피드백을 반복해서 받는 국내 신입·주니어 개발자를 제안한다. 전체 직군을 처음부터 대상으로 삼지 않는다.

| 실제 상황 | 서비스가 줄여야 할 일 |
| --- | --- |
| GPT에서 받은 수정안을 문서에 붙여 넣다가 이전 표현을 잃는다. | 수정 전후 비교와 복원으로 다시 찾는 시간을 줄인다. |
| 기업별로 같은 경험을 다르게 쓰다가 회사명이나 요구사항이 섞인다. | 지원 건마다 공고·문항·답변을 분리하고 복제 출처를 남긴다. |
| 면접 연락을 받았는데 어떤 내용으로 제출했는지 헷갈린다. | 확정해 둔 제출본에서 바로 준비를 시작한다. |
| 공고 문항, 마감일을 여러 도구에 옮겨 적는다. | 한 번 확인한 정보를 작성 화면과 캘린더에서 함께 쓴다. |

이 문제들이 실제로 얼마나 자주 발생하는지는 사용자 관찰로 확인해야 한다. 문서를 거의 수정하지 않거나 지원 건이 적은 사람에게는 새 도구를 배우는 비용이 더 클 수 있다.

## 4. 핵심 사용 흐름

### 공고를 가져오고 확인한다

첫 버전은 URL·스크린샷·텍스트 원문을 보관하고 사용자가 회사·직무·마감일·자소서 문항·글자 수 조건을 입력한다. 주요 업무와 요구사항도 직접 정리할 수 있다. URL 저장이 해당 사이트의 본문 자동 수집을 뜻하지는 않는다. 이후 자동 추출을 추가할 때 원문과 추출 결과를 함께 보여 주고 사용자가 확인한 뒤 적용한다.

로그인이 필요한 문항, 잘린 이미지, 날짜가 없는 공고는 자동으로 완성하지 않는다. 확인되지 않은 항목은 비워 두고 수동 입력을 받는다. 원본 URL·이미지와 확인 시점을 보관한다. 마감 시간이 없으면 임의로 23:59를 지정하지 않으며 상시채용과 날짜 미상도 구분한다.

### 지원할 공고를 고른다

관심 공고를 저장하고 사용자가 지원 여부를 정한다. 지원 건에 공고 요건과 관련 경험 메모를 남길 수 있다. 자동 적합도 분석과 우선순위 추천은 이후 검토하며, 첫 버전에서 합격 확률을 산출하지 않는다.

### 문항별로 쓰고 버전을 남긴다

문항, 글자 수 조건, 사용자가 입력·확인한 공고 정보를 보면서 텍스트로 작성한다. 자동 저장은 작업 유실을 막고 버전 저장은 초안·피드백 반영·제출 후보처럼 의미 있는 시점을 남긴다. 모든 키 입력을 버전 목록에 노출하지 않는다.

이전 버전과 문항별 차이를 비교한다. 작성 중인 답변에서 이전 저장본과 달라진 부분을 바로 확인하고, 다른 두 버전도 선택해 비교한다. 추가·삭제·수정된 문항과 문장을 구분하고, 바뀌지 않은 부분은 접어 한눈에 읽히도록 한다. 수정 이유를 선택적으로 적고 선택한 문항의 답변을 복원한다. 복원도 그 문항의 새 버전으로 남긴다. 다른 문항의 작성 내용과 버전 이력은 바뀌지 않는다. 다른 기업용으로 복제할 때에는 원래 지원 건의 글과 제출본이 바뀌지 않는다.

2026-11-07 Docsa 코드를 읽어 확인했다. `DocumentCompareView`는 블록의 대응 관계를 정렬한 뒤 `diff_main`·`diff_cleanupSemantic`으로 블록 안의 바뀐 문자열 구간을 구분한다. 자소서는 문단 전체를 강조하는 대신 바뀐 낱말·구절을 표시하고, 병합도 해당 구절을 선택해 결과에 반영하는 방향이다. 키워드는 여기서 변경 구간을 뜻하며 AI의 주요어 추출 기능이 아니다. 문항별 텍스트 구조에 대한 실제 코드 재사용·동작 검증은 구현 계획에서 확인한다. ### 제출본과 일정을 관리한다

실제 채용 사이트에서 지원한 뒤 사용자가 제출본과 제출 시각을 지정한다. 서비스 안의 제출본 지정은 채용 사이트에 실제 접수됐다는 검증을 뜻하지 않는다.

제출본에는 해당 시점의 문항·답변·글자 수 조건·공고 맥락을 고정한다. 문항마다 선택한 답변 버전의 식별자와 당시 내용을 묶어 보관하며, 개별 문항의 버전 번호가 같을 필요는 없다. 이후 초안 수정으로 제출본이 바뀌지 않아야 한다. 잘못 지정한 경우 수정 기록을 남기고 다시 지정한다.

첫 버전의 지원 상태는 관심·작성 중·제출·전형 진행·종료로 두고 종료 결과와 면접·과제 일정은 별도로 기록한다. 캘린더에서는 마감과 전형 일정을 구분한다. 초기에는 사용자가 상태와 일정을 확인하며 외부 캘린더 동기화는 후순위로 둔다.

개인 항목은 회사·공고 없이 추가하며 기본 관리 방식은 일반 일정이다. 제목·날짜와 선택 시간을 지정하고, 시간이 없으면 종일로 취급한다. 완료 관리가 필요한 항목만 체크리스트를 선택한다. 캘린더의 모든 개인 항목에 체크박스를 강제하지 않는다. 체크리스트의 완료·취소는 지원 상태와 별도로 관리한다. 외부 캘린더 동기화와 알림 서비스는 후순위로 둔다.

지원 일정과 개인 할 일은 시작일·종료일로 기간을 설정할 수 있다. 하루 항목은 두 날짜를 같게 두고, 종일 기간의 종료일은 화면에서 포함되는 마지막 날짜다. 예를 들어 11월 16일~18일은 3일 동안 표시한다. 시간 있는 일정에는 시작·종료 시각을 지정하고 종료 시점이 시작보다 빠르면 입력을 유지한 채 수정 안내를 표시한다. 종일 항목에서는 시간 입력을 숨기고 날짜만 관리한다. 지원 마감일은 접수 기한이라는 기존 의미를 유지하며 기간 일정의 종료일과 혼동하지 않는다.

캘린더의 여러 날 항목은 날짜 칸을 가로지르는 하나의 막대로 표시한다. 주·월 경계를 넘으면 각 행·현재 월에서 잘라 이어지는 항목임을 보여 준다. 표시 조각마다 별도 일정을 만들지 않으며 하나의 항목을 수정·완료한다. 기간 중인 개인 할 일을 완료하면 해당 항목 전체의 완료 상태가 바뀌고 지원 단계는 바뀌지 않는다.

### 매일 반복·선택형 체크리스트·색상

일반 일정과 체크리스트 모두 반복 안 함·매일을 선택할 수 있다. 첫 일정의 시작·종료와 별도로 반복 종료 없음 또는 종료 날짜를 지정한다. 한 번의 일정이 며칠 동안 이어지는 기간과 매일 새 회차가 생기는 반복은 구분한다. 매주·매월 등 다른 반복 주기는 이번 범위에 추가하지 않는다.

반복 체크리스트는 회차별 날짜에 완료 상태를 둔다. 11월 19일 완료가 20일이나 전체 반복의 완료로 처리되지 않는다. 특정 날짜만 건너뛰거나 수정하는 경우와 전체 반복 수정의 범위를 구분하며 기존 완료 이력을 유지한다. 지원 단계는 바뀌지 않는다.

개인 일정·체크리스트에 기본색 포함 6개 프리셋을 제공하는 방향을 제안하고 Figma에 반영한다. 색은 사용자 분류를 위한 표시이며 완료·미완료나 합격·불합격의 의미를 강제하지 않는다. 제목·반복 표시·체크 상태를 함께 제공하며, 색만으로 상태를 구분하지 않는다. 자유 색상 입력·카테고리별 자동 색상·태그 관리로 확장하지 않는다.

### 후속 공고 등록: 공고별 채용 절차와 현재 단계

2026-11-01 사용자 결정. 공고를 등록할 때 해당 공고의 채용 절차를 읽어 제안하고, 사용자가 확인·수정한 뒤 지원 현황의 단계 선택에 반영한다. 회사가 같아도 직무·채용 유형·시기별로 절차가 다를 수 있으므로 회사 전체에 하나의 고정 절차를 강제하지 않고 공고·지원 건 단위로 관리한다.

예를 들어 A 공고는 ‘서류 → 코딩테스트 → 기술면접 → 최종면접’, B 공고는 ‘서류 → 과제 → 실무면접 → 처우협의’로 등록할 수 있다. 이는 가상의 예시이며 실제 회사의 절차를 설명한 것이 아니다. 단계 이름·순서·추가·삭제를 사용자가 조정할 수 있게 한다. 생략되거나 바뀐 단계 때문에 진행 상태 변경이 막히지 않도록 한다.

URL·이미지·텍스트에서 추출한 절차는 원문과 대조해 확인한 뒤 적용한다. 절차가 없거나 판독이 불확실하면 임의의 코딩테스트·면접 단계를 만들지 않고 수동 입력을 받는다. 자동 인식은 공고 자동 추출과 함께 후속 범위에 둔다. [공고 등록 미리보기](../design/06-posting-registration.md)에서는 가상의 예시 결과와 수동 입력을 구분하고 단계 수정·저장·지원 현황 반영 흐름을 연결했으며, 실제 자동 인식은 구현하지 않았다.

관심·작성 중·제출·전형 진행·종료는 전체 지원 활동을 묶어 보는 공통 분류로 유지하고, 실제 진행 중인 공고에서는 ‘과제’·‘기술면접’처럼 해당 공고의 현재 단계를 상태 선택과 표시에서 사용한다. 공통 분류와 공고별 전형 단계를 하나의 고정 목록으로 합치지 않는다. 전체 목록 필터는 공통 분류를 기준으로 비교할 수 있게 하되, 화면에 두 상태 선택기를 반드시 나란히 놓는다는 뜻은 아니다. 구체적인 표시는 다음 공고 등록·지원 현황 설계에서 확인한다.

현재 단계는 사용자가 확인해 선택한다. 절차를 인식했다는 이유나 일정이 지났다는 이유로 합격·통과·제출·다음 단계 진입을 자동 확정하지 않는다. 종료 결과는 전형 단계와 구분한다. 면접·과제 일정은 해당 지원 건의 실제 단계와 연결하고, 절차를 나중에 고쳐도 이미 기록한 일정·단계 이동 이력이 유실되거나 다른 단계에 잘못 붙지 않도록 한다.

후속 검증은 서로 다른 절차의 두 공고에서 각기 다른 단계 선택지가 보이는지, 인식 오류와 절차 미기재를 수동 수정할 수 있는지, 변경 후 일정과 현재 단계가 유지되는지에 둔다. 실제 추출 모델·저장 구조·API는 구현 계획에서 결정한다.

### 이후 확장: 제출한 내용으로 면접을 준비한다

예상 질문 정리 페이지에서는 공고와 제출본에서 질문·꼬리 질문을 만들고, 근거가 된 자소서 주장·문항·직무 요건을 표시한다. 사용자가 질문을 추가·수정하고 준비할 질문을 정리한다. 별도의 공통 경험 관리 기능은 만들지 않는다.

모의면접 모드는 Voice API로 질문을 듣고 음성으로 답변하는 흐름이다. 타이핑 답변 입력이나 텍스트 면접 모드를 선행하지 않는다. 기준 제출본·공고와 질문 범위를 확인하고 마이크 사용을 허용한 뒤 시작한다. 듣기·답변 인식·다음 질문 생성·일시정지·연결 오류 상태를 구분한다. 일시정지 때에는 음성 입력과 진행을 멈추고, 종료 후 음성 전사와 질문별 피드백으로 복기한다. 연습 중·종료 후 기록이 기준 제출본을 수정하지 않는다.

답변 피드백은 빠진 근거, 불명확한 역할, 설명하지 못한 기술적 선택을 짚는다. 한국어 인식, 응답 지연, 말 끊기, 마이크 권한 거절, 연결 중단과 비용을 실제로 측정한다. 음성 제공자와 예산·세션 제한을 확인하기 전에는 실제 녹음이나 모델 연결이 된 것으로 표시하지 않는다. 원음 저장 여부와 보관·삭제 정책은 구현 전에 정하며, 디자인에 전사를 표시했다는 이유만으로 원음 영구 저장을 가정하지 않는다.

## 5. 개인 AI와 서비스의 역할

2026-11-07 사용자 결정으로 첫 실사용 경험은 JaNovel 웹사이트 안에서 개인 AI와 채팅하는 것으로 변경했다. 고객이 허용한 로컬 자료와 해당 공고·문항·자소서 버전을 에이전트가 참고하고, 서비스가 피드백·근거·수정 후보·채택 이력을 정리한다. 수정 후보는 사용자가 비교해 채택할 때 새 버전이 되며 원문을 덮어쓰지 않는다. 모델·에이전트 실행과 인증은 서비스 UI와 별개로 검증해야 한다. MCP 서버를 중간에 두는 방식도 검토하되 서버를 등록했다는 이유만으로 웹 채팅에서 개인 AI를 실행할 수 있다고 가정하지 않는다.

### 외부 ChatGPT + MCP 흐름: 이전 기본안의 참고 시나리오

아래는 외부 AI 호스트에서 서비스 도구를 쓰는 참고 흐름이다. 현재 필수 웹 채팅 경험의 대체 완료 기준으로 사용하지 않는다. 자료 조회·수정 후보 계약은 내부 채팅에서도 재사용할 수 있는 후보다.

1. 사용자가 ChatGPT에서 특정 지원 건과 자소서 버전을 지정해 피드백을 요청한다. 여러 지원 건에 `v2`가 있을 수 있으므로 회사·공고 또는 지원 건 식별자를 함께 고른다.
2. ChatGPT가 서비스의 읽기 도구 `get_review_context(application_id, question_id, answer_version_id)`를 호출한다. 서비스는 그 사용자의 접근 권한을 확인하고 자소서 본문·공고·문항·검증된 경험 근거·평가 기준과 각 버전 식별자를 하나의 응답으로 준다.
3. ChatGPT가 이 맥락을 참고해 분석하고 사용자에게 피드백을 보여 준다. 결과에는 사실 확인이 필요한 주장, 문항·직무 연결, 문장 수정 이유를 구분한다. 서비스가 준 기준은 참고 자료이며 AI의 상위 지침을 강제로 바꾸는 수단이 아니다.
4. 쓰기 도구를 사용할 수 있고 사용자가 저장을 요청하면 `save_review_candidate`로 원본 버전에 연결된 수정 후보를 저장한다. 쓰기를 사용할 수 없으면 사용자가 결과를 서비스에 붙여 넣어 후보로 저장한다. 사용자는 서비스에서 원문과 후보의 차이를 확인한 뒤 채택한다. 채택 시 새 버전을 만들며, 후보 저장 자체는 본문 수정이나 채택을 뜻하지 않는다.

첫 구현은 도구 중심으로 설계한다. MCP에는 Resources와 Prompts 개념도 있지만 연결한 AI 호스트가 이를 자동으로 조회하거나 우선 적용한다고 가정하지 않는다. 별도 프롬프트 템플릿은 서비스에서 버전을 관리하고 읽기 도구의 평가 기준으로 함께 전달한다. [MCP 구성 요소](https://developers.openai.com/plugins/concepts/mcp-server) · [도구 설계](https://developers.openai.com/plugins/plan/tools)

원격 MCP 서버는 서비스 백엔드의 공통 HTTPS 주소를 사용하고, 로그인·권한으로 사용자 데이터를 구분하는 방향을 권고한다. 사용자 ID나 장기 비밀 토큰을 URL 자체에 넣어 신원을 대신하지 않는다. 구현 계획에서 OAuth 연결과 계정별 접근 검사를 작은 실험으로 확인한다. [MCP 인증 안내](https://developers.openai.com/plugins/build/auth)

MCP 연결만으로 사용자의 전체 대화나 기억을 읽거나, GPT의 최상위 지침을 바꾸는 기능으로 가정하지 않는다. OpenAI 안내상 맞춤 GPT는 이전 대화나 저장된 기억을 사용하지 않는다. 평소의 일반 ChatGPT 대화에 쌓인 맥락과 맞춤 GPT에 올린 자료는 다르게 취급해야 한다. 공식 개발자 문서는 맞춤 MCP 서버의 읽기·쓰기 도구를 안내하지만 실제 개인 계정에서 허용되는 범위는 요금제와 기능 제공 상태를 확인해야 한다. [맞춤 MCP 개발자 문서](https://developers.openai.com/api/docs/guides/custom-mcp-server) · [ChatGPT 맞춤 MCP 안내](https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt) · [맞춤 GPT 안내](https://help.openai.com/en/articles/8554407-gpts-in-chatgpt)

첫 버전은 ① 실제 경험 보존·구체성·본인 기여, ② 문항·직무·회사 적합성, ③ 문장·분량·읽기 쉬움을 모두 평가한다. 사실 보존은 가중 점수보다 필수 조건이다. 근거 없는 경험·성과 수치는 제안에 넣지 않고 확인 질문으로 돌린다. 각 피드백은 대상 구절, 평가 항목, 이유, 확인된 근거 또는 부족한 근거, 수정 제안을 연결한다. 면접에서 설명 가능한지도 확인한다.

같은 공고·문항·경험·초안으로 평소 GPT 피드백과 서비스 맥락·기준을 제공한 피드백을 비교한다. 세 항목 모두에서 사용자가 채택할 만한 수정이 늘어나는지 보고, 사실 왜곡이 있으면 품질 실패로 기록한다. MCP 경로 자체가 글의 품질을 높인다고 가정하지 않는다. [LLM 정확도 개선 지침](https://developers.openai.com/api/docs/guides/optimizing-llm-accuracy)

외부 AI 결과는 기존 본문 덮어쓰기보다 새 후보 버전 생성으로 시작한다. 쓰기 가능한 MCP 경로를 쓸 경우 요청 재시도에 중복 버전이 생기지 않고 오래된 초안을 기준으로 한 수정이 최신 작업을 덮지 않는지 확인한다. 외부 AI에 보낼 자료는 사용자가 선택하고 연결 해제·데이터 내보내기·삭제 경로를 둔다.

AI 호출 방식과 무관하게 서비스가 공고 원문·확인본, 문항, 답변 버전, 사용자가 확인한 경험 근거, 평가 기준의 버전, 피드백을 보관한다. 피드백에는 대상 답변 버전·평가 항목·대상 구절·이유·근거·제안과 생성 경로를 남긴다. 나중에 내부 AI API를 붙일 때 서비스가 같은 맥락을 구성해 호출하고 동일한 피드백 구조로 저장하면 기존 비교·채택 화면과 기록을 재사용할 수 있다. 이는 호출 경로 추가이며 설정 하나를 바꾸는 작업은 아니다. 개인 GPT의 대화·기억은 API로 자동 이전되지 않으므로 유용한 경력·경험 자료는 사용자가 서비스에 명시적으로 저장해야 한다. [OpenAI MCP 도구](https://developers.openai.com/api/docs/guides/tools-connectors-mcp) · [Responses API](https://developers.openai.com/api/reference/responses/overview) · [구조화 출력](https://developers.openai.com/api/docs/guides/structured-outputs)

### 서비스 내부 채팅의 실행·인증 경로: 기술 검증 필요

서비스 내부 채팅은 사용자 확정 요구다. 아래 방식 중 고객의 에이전트·로컬 자료·이용 권한을 연결할 수 있는 한 경로를 먼저 시험한다. MCP는 자료·기능 연결이고, 모델 호출 권한과 비용 경로는 별개다. 외부 호스트만으로 성공한 실험을 내부 채팅 완료로 보고하지 않는다.

| 경로 | 모델 호출과 자료 연결 | 현재 판단 |
| --- | --- | --- |
| 외부 ChatGPT + MCP | ChatGPT에서 대화하고 서비스의 MCP 도구를 호출 | 보조 연동·계약 검증 후보. 현재 필수 웹 채팅의 기본 경로가 아님 |
| 내부 채팅 + 일반 API | 서비스가 별도 API 자격으로 모델을 호출하고 필요한 자료·도구를 제공 | 구현 가능 후보. API 비용을 따로 계산해야 함 |
| 내부 채팅 + Sign in with ChatGPT(SIWC) | 사용자가 구독 사용 권한을 승인하면 허용된 모델 요청에 구독 사용량 활용 | 앱 유형·승인·기능 제한 확인 후 실험할 후보. 로그인만으로 사용 권한이 생기지 않음 |

SIWC 공식 안내는 오픈소스·로컬 앱 경로와 유료·원격 호스팅 서비스의 접근 신청을 구분한다. 오픈소스 앱을 원격 VM에서 개인적으로 실행하는 절차도 별도 제공한다. 따라서 홈서버라는 위치만으로 가능·불가를 판정하지 않는다. 본인용 자가 호스팅과 여러 사용자에게 제공할 웹서비스를 나누어 확인한다. 현재 프로젝트가 해당 경로에 적합한지, 실제 계정에 권한이 부여되는지는 미검증이다. 개인용 실험 성공을 공개 서비스 제공 승인으로 해석하지 않는다. [SIWC 개요](https://developers.openai.com/siwc/token-sharing-open-source) · [자가 호스팅 VM 안내](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms)

SIWC의 현재 프리뷰에서는 OpenAI가 실행하는 hosted MCP/connectors 도구를 지원하지 않는다. 일반 Responses API의 MCP 기능을 이 경로에서도 그대로 사용할 수 있다고 가정하면 안 된다. 내부 채팅에 MCP를 결합한다면 우리 애플리케이션이 지원되는 function/custom 도구 요청을 받아 MCP 클라이언트로 실행하고 결과를 모델에 돌려주는 구성을 검토한다. 한 백엔드 안에서는 공통 서비스 로직을 직접 호출하는 대안도 있다. 이는 문서에 근거한 설계 후보이며 아직 구현·시험하지 않았다. [SIWC 프리뷰 제한](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)

SIWC는 기존 ChatGPT 대화·기억을 읽을 권한을 주지 않는다. 서비스가 경험 자료와 채팅 맥락을 관리해야 한다. 현재 HTTP 경로는 필요한 이력을 매 요청에 제공해야 하며, 음성 입력·전사 지원도 이 경로의 전제로 삼지 않는다. 내부 채팅이 채택되더라도 수정 후보 저장 → 차이 확인 → 사용자 채택 규칙은 유지한다. [SIWC 개요](https://developers.openai.com/siwc/token-sharing-open-source) · [프리뷰 제한](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)

검증 순서는 ① 개인용 실행과 공개 웹서비스의 자격 구분, ② 승인된 경로에서 구독 사용 동의·모델 목록·응답 수신 확인, ③ 선택한 자소서 조회와 수정 후보 저장, ④ 사용 한도 도달·연결 해제·대화 재개 확인이다. 실패 시 유료 API로 자동 전환하지 않는다. 이번에는 공식 문서 조사만 했으며 계정 연결, 토큰 발급·이전, 접근 신청, 모델 호출은 수행하지 않았다. 지원 조건과 실험 결과를 확인한 뒤 내부 채팅을 포함할 단계와 배포 방식을 결정한다.

## 6. 첫 버전 확정 범위와 이후 확장

| 단계 | 제공 범위 | 다음 단계로 넘어갈 근거 |
| --- | --- | --- |
| 개인 실사용 | 공고 원문 입력·보관, 문항 수동 입력, 텍스트 작성, 자동 저장, 문항별 변경 구절 확인·복원, 제출본, 상태·기본 캘린더, 웹서비스 안에서 개인 AI와 채팅해 수정 후보를 받아 저장하는 한 경로. 개인 에이전트·로컬 자료·실행·인증 연결을 작은 실험으로 검증 | 실제 지원에서 변경점을 빨리 이해하고 세 항목의 피드백을 쓸 만한지 확인 |
| 소규모 검증 | 공고·문항·채용 절차 자동 추출과 확인, 공고별 현재 단계 관리, 예상 질문 정리, 필요할 때 서비스 내부 AI API 경로 비교 | 다른 사용자도 도움 없이 반복해서 사용하고 자동화가 수동 입력보다 시간을 줄임 |
| 비용 검증 후 확장 | Voice API 기반 모의면접, 개인 맞춤 주간 추천과 유료 실험. 모의면접은 텍스트 입력을 선행하지 않음 | 품질·운영비·지불 의사를 확인 |

URL·이미지 입력은 첫 단계부터 보존한다. 자동 분석은 다음 단계로 미룬다. AI 피드백과 서비스 내부 채팅은 첫 실사용 버전의 필수 범위다. 내부 채팅에서 개인 AI에 요청하고 허용된 로컬 자료를 참고해 수정 후보를 반환하는 경로를 먼저 검증한다. 연결이 막히면 내부 채팅은 미완료로 남기며 실행·인증 방식을 다시 검토한다. 수동 전달과 외부 AI 사용은 자료·품질 검증에는 활용할 수 있으나 필수 내부 채팅의 구현 완료로 대신하지 않는다. 음성 면접과 추천 기능을 전체 구상에서 제외하는 뜻은 아니다.

사용자 후속 요청으로 스냅샷·분기·병합을 디자인했다. 2026-11-07에는 Docsa를 참고해 비교의 강조와 병합의 선택 단위를 바뀐 낱말·구절로 맞추고 원문·편집 결과·수정본 3열로 수정했다. 문항 단위로 기존 기록을 유지하며 분기와 병합 결과를 새 스냅샷으로 남긴다. 실제 저장·API 구조와 자동 충돌 해결은 후속 구현 계획에서 확정한다. 초기에 보류할 항목은 범용 이력서 편집기, 그래프 직접 편집·복잡한 자동 병합, 모든 채용 사이트 자동 수집, 자동 지원, 합격 확률 점수다.

## 7. 주간 추천과 비용

현재 월요일 GPT 예약을 기준선으로 삼는다. Java/Spring Boot 적합성, Toss·Naver·Kakao·LG CNS·Samsung SDS의 관련 채용 기회, 요구사항, 경험과 맞는 점, 보완점, 우선순위를 정리하는 방식이다. 이 문서 작업에서 기존 예약을 변경하지 않는다.

제품의 추천에는 출처, 확인 시점, 마감 여부, 제외 조건, 중복 제거를 더하고 선택한 공고를 바로 지원 건으로 연결한다. 관심 기업이라고 관련 공고가 없는 때에도 억지로 포함하지 않는다. 요약만으로 유료 가치를 가정하지 않고 기존 예약보다 실제 지원할 공고를 더 잘 찾는지 확인한다.

추가 현금 지출을 피하려면 초기에는 기존 홈서버와 이미 사용하는 개인 GPT·수동 입력을 우선 검토한다. MCP 연결 가능 여부와 ChatGPT 이용 조건은 확인해야 하며 개인 GPT 이용 권한을 일반 API 사용 예산으로 간주하지 않는다. SIWC 구독 사용은 별도 권한과 앱 자격을 충족해야 하는 후보로 5절에 구분했다. 전기·유지보수 비용은 남고 이후 API 기반 추출·검색·음성 비용은 서버 비용과 별개다. AWS 무료 플랜에도 대상·기간·사용량 조건이 있으므로 장기 무상 운영의 근거로 삼지 않는다. [AWS 무료 플랜 FAQ](https://aws.amazon.com/free/free-tier-faqs/)

MCP 자체가 토큰을 줄여 주지는 않는다. 도구 설명, 호출과 반환 자료도 모델이 읽으므로 같은 본문을 직접 붙여 넣는 것보다 늘 수 있다. 필요한 문항·관련 경험·해당 평가 기준만 전달하고 서버에서 변경점을 계산해 반환하면 전체 자료를 매번 보내는 방식보다 줄일 여지는 있다. 전체 문장 검토가 필요할 때에는 차이만 보내 맥락을 잃지 않도록 한다. 실제 절감은 동일 작업의 호출·반환량을 비교해야 하며 Plus 사용 한도가 토큰 수에 단순 비례한다고 가정하지 않는다. [OpenAI MCP 도구 안내](https://developers.openai.com/api/docs/guides/tools-connectors-mcp)

서비스가 MCP로 저장 자료만 제공하고 외부 AI가 분석한다면 그 분석을 위한 서비스 측 모델 API 호출 비용은 발생하지 않는다. 서버 운영비와 사용자의 AI 이용 조건은 남는다. 자동 추출이나 내부 AI API를 추가하면 호출 경로별 비용과 한도를 계산한다. 일반 API는 별도 과금이고, 승인된 SIWC 경로는 사용자 구독 사용량을 소모한다.

AI 기능을 붙이기 전 사용자당 월 예상 비용과 허용량을 계산한다. 홈서버 선택은 여유 자원과 백업·복구 가능성을 확인한 뒤 확정한다. 외부 사용자를 받기 전에는 사용자별 데이터 접근 분리와 복구를 점검한다.

## 8. Docsa 재사용과 설계 기준

별도 저장소와 배포·데이터 영역을 전제로 시작한다. Docsa의 문서·저장·버전·비교 구조는 재사용 후보지만 자소서의 문항 단위와 제출본 고정 규칙에 맞는지 먼저 확인한다. 현재 검토는 README와 구조 수준이며 상세 코드 재사용 판정은 아직 하지 않았다.

데이터의 중심은 지원 건이다. 공고 원문, 문항 묶음, 작업 중 답변, 저장 버전, 제출본, 일정, 피드백을 연결한다. 2026-11-01 사용자 결정에 따라 저장·비교·복원과 그래프의 기본 단위는 개별 문항의 답변이다. 문항마다 작업 중 답변, 저장 버전, 부모 버전과 피드백 대화를 독립적으로 관리한다. Q1의 v2와 Q2의 v2는 서로 다른 기록이다. 한 문항을 저장하거나 AI 수정안을 채택해도 다른 문항의 이력은 바뀌지 않는다. 전체 자소서의 제출본은 문항별 선택 버전을 고정해 묶은 스냅샷으로 관리한다. 문항이 바뀌어도 이전 버전을 재현할 수 있어야 한다.

사용자에게는 버전 저장·비교·복원·다른 지원용 복제로 표현한다. 기존 내부 구조에 브랜치가 있어도 사용자가 Git 개념을 배울 필요는 없다. 자소서 입력에서는 이미지 기능을 숨기되 공고 이미지 보관과 분리한다. 이력서 확장은 별도 수요가 확인되면 검토한다.

포트폴리오에는 실제로 발견하고 해결한 문제만 기록한다. 저장 충돌, 버전 복원, 외부 AI 중복 저장, 문항 추출 오류, 비용과 지연은 관찰할 후보이며 아직 성과가 아니다. 원래 Docsa의 팀 기여와 신규 프로젝트 기여를 구분하고 재사용 권한도 확인한다.

### 추가 검토 모델을 쓰는 경우

기획과 구현 계획처럼 뒤에 영향을 크게 주는 판단에는 Astra를 사용하고, 반복 제작과 수정은 Sol을 기본으로 둔다. 단계마다 두 모델을 모두 돌리지는 않는다.

- 와이어프레임의 사용 흐름이 계속 꼬이거나 요구가 충돌하면 Astra · High로 해당 쟁점만 검토한다.
- Figma의 여러 화면과 컴포넌트를 함께 조정할 때는 Sol · High로 올린다. 디자인 판단은 사용자가 실제 화면을 보고 확인한다.
- 구현 중 원인이 불명확한 저장 충돌, 복원 오류, 권한 문제나 큰 구조 변경이 필요하면 Astra · High로 원인과 대안을 검토한 뒤 Sol로 구현을 이어 간다.
- 출시 전 중요한 변경에는 Astra · High로 코드와 테스트 근거를 검토한다. 모델의 검토 의견만으로 테스트 통과를 대신하지 않는다.
- 실사용 결과를 보고 핵심 범위나 유료화를 바꿀 때는 Astra · High로 판단 근거를 다시 검토한다.

기본 수준으로 해결되지 않는 복잡한 분석에 한해 Extra high를 검토한다. 매 작업에 가장 높은 추론 수준을 고정하지 않는다. 모델을 바꿀 때에는 최신 기획서, 디자인, 관련 코드와 미해결 쟁점을 함께 전달한다. 앱에서 해당 모델이나 추론 수준을 선택할 수 있는지도 작업 시작 시 확인한다.

이 배정은 2026-10-16에 확인한 공식 안내를 바탕으로 한 프로젝트 운영 권고다. 공식 안내는 Astra를 까다로운 추론과 작업에, GPT-6.1 Sol을 품질·시간·비용을 함께 고려하는 복잡한 작업에 제시한다. 단계별 우열을 이 프로젝트에서 실험한 결과는 아니며, 같은 작업의 결과와 사용량을 보고 조정한다. [OpenAI 모델 선택 안내](https://developers.openai.com/api/docs/guides/model-selection)

## 10. 첫 버전의 완료 기준

다음은 구현 후 확인할 기준이며 현재 통과한 결과가 아니다. 작업 순서와 구체적인 테스트 방식은 구현 계획에서 정한다.

| 시나리오 | 확인할 동작 |
| --- | --- |
| 공고 등록 | URL·이미지·텍스트 원문을 지원 건에서 다시 볼 수 있고, 문항·조건을 수동으로 수정할 수 있다. 날짜 미상·상시채용을 구분하며 모르는 마감 시각을 만들어 넣지 않는다. |
| 작성과 저장 | 작업 중 내용의 자동 저장과 명시적 버전 저장을 구분한다. 실패한 저장을 성공으로 표시하지 않고 입력을 유지해 재시도할 수 있다. 첫 버전의 글자 수는 공백 포함·제외를 함께 보여 주며 채용 사이트의 별도 계산 규칙까지 보장하지 않는다. |
| 비교와 복원 | 작성 중 내용과 저장본 또는 선택한 두 저장본을 문항별로 비교한다. 문항 추가·삭제·순서 변경을 구분한다. 선택한 문항 복원 시 그 문항에만 새 버전이 생기고 이전 버전은 재현할 수 있다. 문항별 그래프·초안·번호가 분리되며 다른 문항은 바뀌지 않는다. |
| 기업별 분리 | 다른 지원 건으로 복제한 글을 수정해도 원래 지원 건의 내용·이력·제출본이 변하지 않는다. |
| 제출본 | 지정 시점의 문항·답변·조건·공고 맥락을 고정한다. 이후 작성이나 공고 변경에도 유지하며 재지정 이력을 남긴다. 제출본 지정만으로 외부 사이트 접수 성공을 표시하지 않는다. |
| 상태와 일정 | 지원 상태와 마감·면접·과제 일정을 직접 수정하고 목록과 기본 캘린더에서 같은 정보를 본다. 개인 할 일을 회사 연결 없이 추가하고 수정·완료·완료 취소할 수 있으며, 지원 단계는 바뀌지 않는다. 날짜가 없는 지원 일정은 날짜 미확인 목록에서 찾을 수 있다. 외부 캘린더 동기화와 알림 발송은 포함하지 않는다. |
| AI 맥락 전달 | 지원 건·문항·답변 버전을 함께 식별해 관련 공고·확인된 경험·평가 기준 버전과 전달한다. 응답이 해당 문항의 원본 버전과 연결되며 다른 문항에 적용되지 않는다. 불필요한 다른 지원 건과 전체 버전 이력을 보내지 않는다. |
| 피드백 확인 | 사실·경험 보존, 문항·직무 적합성, 문장 품질을 함께 검토한다. 대상 구절·이유·근거·제안을 연결하고 근거 없는 경험과 수치를 사실처럼 채택하지 않는다. AI가 사실을 만들어 내면 품질 실패로 기록한다. |
| 수정 후보 채택 | 피드백과 후보를 원본 버전에 연결해 저장하고 사용자가 차이를 본 뒤 새 버전으로 채택한다. 검토 사이 원본 작업이 바뀌면 이를 알려 다시 비교하게 한다. 자동 덮어쓰기는 없다. |
| 내부 채팅과 개인 AI 연결 | 실제 지원되는 개인 AI 계정·실행 경로에서 웹 채팅 요청·응답·진행 상태를 확인하고, 허용한 로컬 자료와 선택한 공고·문항을 참고한 후보를 반환한다. MCP를 쓰면 조회·후보 저장과 중복 요청 처리를 검증한다. 외부 호스트나 수동 전달 성공을 내부 채팅 완료로 기록하지 않는다. |
| 접근과 데이터 관리 | 웹·MCP 모두 다른 사용자 식별자를 넣어 자료를 조회·수정할 수 없다. 연결 해제 후 해당 권한으로 접근할 수 없고, 사용자는 지원 자료를 내보내거나 삭제할 수 있다. 삭제 전 대상 범위를 확인한다. |

제품의 유용성은 별도로 검증한다. 실제 지원 3건에서 기존 GPT·문서·캘린더 방식과 변경점 확인, 복원, 피드백 반영, 제출본 찾기, 일정 관리의 시간과 실수를 비교한다. AI 평가는 누적 10개 문항을 목표로 하되 자료가 부족하면 검증 중으로 남긴다. 사실 왜곡·글 유실·제출본 변조가 발생하면 확장보다 수정이 먼저다. 등록 작업까지 시간이 줄었다고 미리 가정하지 않는다.

## 11. 선택한 접근과 남은 판단

| 접근 | 장점과 부담 | 결정 |
| --- | --- | --- |
| 버전관리 중심 + 웹 내부의 개인 에이전트 연결 | Docsa를 활용하고 고객의 에이전트가 로컬 자료와 서비스 맥락을 함께 쓰게 한다. 실행 중계·인증·연결 설정이 필요하다. | 사용자 확정 경험. 실제 경로 하나를 먼저 시험하며 중간 MCP 서버는 검토 후보로 둔다. |
| 서비스 내부 AI API부터 제공 | 작성·피드백을 한 화면에서 연결하기 쉽다. 경험 자료를 별도로 모아야 하고 호출 비용과 품질 관리가 필요하다. | 후속 비교 대상. 동일한 지원 자료·평가 기준·피드백 기록을 재사용하도록 한다. |
| 수집·추천·작성·음성 면접을 동시에 제공 | 전체 취업 흐름을 묶을 수 있지만 비용과 구현 범위가 커지고 핵심 가치 검증이 늦어진다. | 첫 버전에서 제외하고 실제 사용 근거로 순차 확장한다. |

현재 기획은 본인의 자소서 수정·제출 관리에 유용할 것이라는 가설에 근거한다. 경쟁력이 입증되었다거나 좋은 평가 프롬프트만으로 유료화할 수 있다고 결론 내리지 않는다. 특히 버전 저장이 번거롭거나 MCP 연결이 복사·붙여넣기보다 어렵다면 흐름을 단순화해야 한다.

후속 작업은 사용 흐름·와이어프레임 → Figma 디자인 → AI 연결 실험·구현 계획 → 개발 → 실사용이다. 2026-11-08 사용자 지시에 따라 디자인 검토를 먼저 마무리하고 AI 연결 실험은 그다음에 진행한다. 웹 내부 채팅 요구는 유지하되 실제 인증·실행 경로의 제약에 따라 연결 설정 화면을 조정할 수 있다. 현재 Figma 화면·상태와 프로토타입 검증의 한계는 [최신 디자인·전환 검토](../design/16-snapshot-working-draft-comparison.md)를 따른다. AI 실험에서는 실제 계정의 연결·읽기·쓰기와 인증을 확인하며 아직 수행하지 않았다.

기획 단계에서 더 고를 필수 제품 옵션은 없다. 남은 것은 기술 확인과 화면 검토다. 배포 방식은 HTTPS 연결, 홈서버 자원과 백업·복구 조건을 확인한 뒤 구현 계획에서 결정한다. Docsa 코드 가져오기·저장소 구성·구현은 별도 단계이며 이번 확정본 작성에는 포함하지 않았다.
