1. 기획의 결론

자소서를 여러 번 고치고 여러 회사에 지원하는 과정에서, 무엇을 왜 바꿨고 실제로 무엇을 제출했는지 남기는 서비스다. 공고와 문항, 수정 이력, 제출본을 한 지원 건에 묶고 면접 준비에서 다시 꺼내 쓴다.

개인용으로 먼저 만들어 검증할 가치는 있다. 다만 버전관리와 취업 준비 통합 기능 자체는 경쟁 서비스에도 있으므로 사업 경쟁력은 아직 입증되지 않았다. 첫 검증은 무엇이 바뀌었는지 한눈에 확인하는 경험과 AI 피드백이 기존 GPT·문서·캘린더 조합보다 실제로 도움이 되는지에 둔다. 경쟁 근거와 반론은 별도 검토 문서에 정리했다.

3. 누구의 어떤 문제를 푸는가

첫 사용자는 Java/Spring Boot 중심으로 지원하는 본인이다. 초기 검증 대상으로는 여러 기업의 자소서 문항을 작성하고 GPT 피드백을 반복해서 받는 국내 신입·주니어 개발자를 제안한다. 전체 직군을 처음부터 대상으로 삼지 않는다.

실제 상황 서비스가 줄여야 할 일
GPT에서 받은 수정안을 문서에 붙여 넣다가 이전 표현을 잃는다. 수정 전후 비교와 복원으로 다시 찾는 시간을 줄인다.
기업별로 같은 경험을 다르게 쓰다가 회사명이나 요구사항이 섞인다. 지원 건마다 공고·문항·답변을 분리하고 복제 출처를 남긴다.
면접 연락을 받았는데 어떤 내용으로 제출했는지 헷갈린다. 확정해 둔 제출본에서 바로 준비를 시작한다.
공고 문항, 마감일을 여러 도구에 옮겨 적는다. 한 번 확인한 정보를 작성 화면과 캘린더에서 함께 쓴다.

이 문제들이 실제로 얼마나 자주 발생하는지는 사용자 관찰로 확인해야 한다. 문서를 거의 수정하지 않거나 지원 건이 적은 사람에게는 새 도구를 배우는 비용이 더 클 수 있다.

4. 핵심 사용 흐름

공고를 가져오고 확인한다

첫 버전은 URL·스크린샷·텍스트 원문을 보관하고 사용자가 회사·직무·마감일·자소서 문항·글자 수 조건을 입력한다. 주요 업무와 요구사항도 직접 정리할 수 있다. URL 저장이 해당 사이트의 본문 자동 수집을 뜻하지는 않는다. 이후 자동 추출을 추가할 때 원문과 추출 결과를 함께 보여 주고 사용자가 확인한 뒤 적용한다.

로그인이 필요한 문항, 잘린 이미지, 날짜가 없는 공고는 자동으로 완성하지 않는다. 확인되지 않은 항목은 비워 두고 수동 입력을 받는다. 원본 URL·이미지와 확인 시점을 보관한다. 마감 시간이 없으면 임의로 23:59를 지정하지 않으며 상시채용과 날짜 미상도 구분한다.

지원할 공고를 고른다

관심 공고를 저장하고 사용자가 지원 여부를 정한다. 지원 건에 공고 요건과 관련 경험 메모를 남길 수 있다. 자동 적합도 분석과 우선순위 추천은 이후 검토하며, 첫 버전에서 합격 확률을 산출하지 않는다.

문항별로 쓰고 버전을 남긴다

문항, 글자 수 조건, 사용자가 입력·확인한 공고 정보를 보면서 텍스트로 작성한다. 자동 저장은 작업 유실을 막고 버전 저장은 초안·피드백 반영·제출 후보처럼 의미 있는 시점을 남긴다. 모든 키 입력을 버전 목록에 노출하지 않는다.

이전 버전과 문항별 차이를 비교한다. 작성 중인 답변에서 이전 저장본과 달라진 부분을 바로 확인하고, 다른 두 버전도 선택해 비교한다. 추가·삭제·수정된 문항과 문장을 구분하고, 바뀌지 않은 부분은 접어 한눈에 읽히도록 한다. 수정 이유를 선택적으로 적고 선택한 문항의 답변을 복원한다. 복원도 그 문항의 새 버전으로 남긴다. 다른 문항의 작성 내용과 버전 이력은 바뀌지 않는다. 다른 기업용으로 복제할 때에는 원래 지원 건의 글과 제출본이 바뀌지 않는다.

제출본과 일정을 관리한다

실제 채용 사이트에서 지원한 뒤 사용자가 제출본과 제출 시각을 지정한다. 서비스 안의 제출본 지정은 채용 사이트에 실제 접수됐다는 검증을 뜻하지 않는다.

제출본에는 해당 시점의 문항·답변·글자 수 조건·공고 맥락을 고정한다. 문항마다 선택한 답변 버전의 식별자와 당시 내용을 묶어 보관하며, 개별 문항의 버전 번호가 같을 필요는 없다. 이후 초안 수정으로 제출본이 바뀌지 않아야 한다. 잘못 지정한 경우 수정 기록을 남기고 다시 지정한다.

첫 버전의 지원 상태는 관심·작성 중·제출·전형 진행·종료로 두고 종료 결과와 면접·과제 일정은 별도로 기록한다. 캘린더에서는 마감과 전형 일정을 구분한다. 초기에는 사용자가 상태와 일정을 확인하며 외부 캘린더 동기화는 후순위로 둔다.

후속 공고 등록: 공고별 채용 절차와 현재 단계

2026-11-01 사용자 결정. 공고를 등록할 때 해당 공고의 채용 절차를 읽어 제안하고, 사용자가 확인·수정한 뒤 지원 현황의 단계 선택에 반영한다. 회사가 같아도 직무·채용 유형·시기별로 절차가 다를 수 있으므로 회사 전체에 하나의 고정 절차를 강제하지 않고 공고·지원 건 단위로 관리한다.

예를 들어 A 공고는 ‘서류 → 코딩테스트 → 기술면접 → 최종면접’, B 공고는 ‘서류 → 과제 → 실무면접 → 처우협의’로 등록할 수 있다. 이는 가상의 예시이며 실제 회사의 절차를 설명한 것이 아니다. 단계 이름·순서·추가·삭제를 사용자가 조정할 수 있게 한다. 생략되거나 바뀐 단계 때문에 진행 상태 변경이 막히지 않도록 한다.

URL·이미지·텍스트에서 추출한 절차는 원문과 대조해 확인한 뒤 적용한다. 절차가 없거나 판독이 불확실하면 임의의 코딩테스트·면접 단계를 만들지 않고 수동 입력을 받는다. 자동 인식은 공고 자동 추출과 함께 후속 범위에 둔다. 공고 등록 미리보기에서는 가상의 예시 결과와 수동 입력을 구분하고 단계 수정·저장·지원 현황 반영 흐름을 연결했으며, 실제 자동 인식은 구현하지 않았다.

관심·작성 중·제출·전형 진행·종료는 전체 지원 활동을 묶어 보는 공통 분류로 유지하고, 실제 진행 중인 공고에서는 ‘과제’·‘기술면접’처럼 해당 공고의 현재 단계를 상태 선택과 표시에서 사용한다. 공통 분류와 공고별 전형 단계를 하나의 고정 목록으로 합치지 않는다. 전체 목록 필터는 공통 분류를 기준으로 비교할 수 있게 하되, 화면에 두 상태 선택기를 반드시 나란히 놓는다는 뜻은 아니다. 구체적인 표시는 다음 공고 등록·지원 현황 설계에서 확인한다.

현재 단계는 사용자가 확인해 선택한다. 절차를 인식했다는 이유나 일정이 지났다는 이유로 합격·통과·제출·다음 단계 진입을 자동 확정하지 않는다. 종료 결과는 전형 단계와 구분한다. 면접·과제 일정은 해당 지원 건의 실제 단계와 연결하고, 절차를 나중에 고쳐도 이미 기록한 일정·단계 이동 이력이 유실되거나 다른 단계에 잘못 붙지 않도록 한다.

후속 검증은 서로 다른 절차의 두 공고에서 각기 다른 단계 선택지가 보이는지, 인식 오류와 절차 미기재를 수동 수정할 수 있는지, 변경 후 일정과 현재 단계가 유지되는지에 둔다. 실제 추출 모델·저장 구조·API는 구현 계획에서 결정한다.

이후 확장: 제출한 내용으로 면접을 준비한다

공고 제출본, 사용자가 확인한 경험을 바탕으로 예상 질문과 꼬리 질문을 만든다. 각 질문이 자소서의 어느 주장이나 직무 요건에서 나왔는지 보여 준다. 답변 연습 뒤에는 빠진 근거, 불명확한 역할, 설명하지 못한 기술적 선택을 짚는다.

먼저 텍스트 질문과 답변 기록으로 맥락이 유용한지 확인한 뒤 음성 대화·전사·피드백을 붙이는 순서를 권고한다. 음성 품질은 한국어 인식, 응답 지연, 말 끊기, 비용을 실제로 측정한다.

5. 개인 AI와 서비스의 역할

2026-11-07 사용자 결정으로 첫 실사용 경험은 JaNovel 웹사이트 안에서 개인 AI와 채팅하는 것으로 변경했다. 고객이 허용한 로컬 자료와 해당 공고·문항·자소서 버전을 에이전트가 참고하고, 서비스가 피드백·근거·수정 후보·채택 이력을 정리한다. 수정 후보는 사용자가 비교해 채택할 때 새 버전이 되며 원문을 덮어쓰지 않는다. 모델·에이전트 실행과 인증은 서비스 UI와 별개로 검증해야 한다. MCP 서버를 중간에 두는 방식도 검토하되 서버를 등록했다는 이유만으로 웹 채팅에서 개인 AI를 실행할 수 있다고 가정하지 않는다.

외부 ChatGPT + MCP 흐름: 이전 기본안의 참고 시나리오

아래는 외부 AI 호스트에서 서비스 도구를 쓰는 참고 흐름이다. 현재 필수 웹 채팅 경험의 대체 완료 기준으로 사용하지 않는다. 자료 조회·수정 후보 계약은 내부 채팅에서도 재사용할 수 있는 후보다.

  1. 사용자가 ChatGPT에서 특정 지원 건과 자소서 버전을 지정해 피드백을 요청한다. 여러 지원 건에 v2가 있을 수 있으므로 회사·공고 또는 지원 건 식별자를 함께 고른다.
  2. ChatGPT가 서비스의 읽기 도구 get_review_context(application_id, question_id, answer_version_id)를 호출한다. 서비스는 그 사용자의 접근 권한을 확인하고 자소서 본문·공고·문항·검증된 경험 근거·평가 기준과 각 버전 식별자를 하나의 응답으로 준다.
  3. ChatGPT가 이 맥락을 참고해 분석하고 사용자에게 피드백을 보여 준다. 결과에는 사실 확인이 필요한 주장, 문항·직무 연결, 문장 수정 이유를 구분한다. 서비스가 준 기준은 참고 자료이며 AI의 상위 지침을 강제로 바꾸는 수단이 아니다.
  4. 쓰기 도구를 사용할 수 있고 사용자가 저장을 요청하면 save_review_candidate로 원본 버전에 연결된 수정 후보를 저장한다. 쓰기를 사용할 수 없으면 사용자가 결과를 서비스에 붙여 넣어 후보로 저장한다. 사용자는 서비스에서 원문과 후보의 차이를 확인한 뒤 채택한다. 채택 시 새 버전을 만들며, 후보 저장 자체는 본문 수정이나 채택을 뜻하지 않는다.

첫 구현은 도구 중심으로 설계한다. MCP에는 Resources와 Prompts 개념도 있지만 연결한 AI 호스트가 이를 자동으로 조회하거나 우선 적용한다고 가정하지 않는다. 별도 프롬프트 템플릿은 서비스에서 버전을 관리하고 읽기 도구의 평가 기준으로 함께 전달한다. MCP 구성 요소 · 도구 설계

원격 MCP 서버는 서비스 백엔드의 공통 HTTPS 주소를 사용하고, 로그인·권한으로 사용자 데이터를 구분하는 방향을 권고한다. 사용자 ID나 장기 비밀 토큰을 URL 자체에 넣어 신원을 대신하지 않는다. 구현 계획에서 OAuth 연결과 계정별 접근 검사를 작은 실험으로 확인한다. MCP 인증 안내

MCP 연결만으로 사용자의 전체 대화나 기억을 읽거나, GPT의 최상위 지침을 바꾸는 기능으로 가정하지 않는다. OpenAI 안내상 맞춤 GPT는 이전 대화나 저장된 기억을 사용하지 않는다. 평소의 일반 ChatGPT 대화에 쌓인 맥락과 맞춤 GPT에 올린 자료는 다르게 취급해야 한다. 공식 개발자 문서는 맞춤 MCP 서버의 읽기·쓰기 도구를 안내하지만 실제 개인 계정에서 허용되는 범위는 요금제와 기능 제공 상태를 확인해야 한다. 맞춤 MCP 개발자 문서 · ChatGPT 맞춤 MCP 안내 · 맞춤 GPT 안내

첫 버전은 ① 실제 경험 보존·구체성·본인 기여, ② 문항·직무·회사 적합성, ③ 문장·분량·읽기 쉬움을 모두 평가한다. 사실 보존은 가중 점수보다 필수 조건이다. 근거 없는 경험·성과 수치는 제안에 넣지 않고 확인 질문으로 돌린다. 각 피드백은 대상 구절, 평가 항목, 이유, 확인된 근거 또는 부족한 근거, 수정 제안을 연결한다. 면접에서 설명 가능한지도 확인한다.

같은 공고·문항·경험·초안으로 평소 GPT 피드백과 서비스 맥락·기준을 제공한 피드백을 비교한다. 세 항목 모두에서 사용자가 채택할 만한 수정이 늘어나는지 보고, 사실 왜곡이 있으면 품질 실패로 기록한다. MCP 경로 자체가 글의 품질을 높인다고 가정하지 않는다. LLM 정확도 개선 지침

외부 AI 결과는 기존 본문 덮어쓰기보다 새 후보 버전 생성으로 시작한다. 쓰기 가능한 MCP 경로를 쓸 경우 요청 재시도에 중복 버전이 생기지 않고 오래된 초안을 기준으로 한 수정이 최신 작업을 덮지 않는지 확인한다. 외부 AI에 보낼 자료는 사용자가 선택하고 연결 해제·데이터 내보내기·삭제 경로를 둔다.

AI 호출 방식과 무관하게 서비스가 공고 원문·확인본, 문항, 답변 버전, 사용자가 확인한 경험 근거, 평가 기준의 버전, 피드백을 보관한다. 피드백에는 대상 답변 버전·평가 항목·대상 구절·이유·근거·제안과 생성 경로를 남긴다. 나중에 내부 AI API를 붙일 때 서비스가 같은 맥락을 구성해 호출하고 동일한 피드백 구조로 저장하면 기존 비교·채택 화면과 기록을 재사용할 수 있다. 이는 호출 경로 추가이며 설정 하나를 바꾸는 작업은 아니다. 개인 GPT의 대화·기억은 API로 자동 이전되지 않으므로 유용한 경력·경험 자료는 사용자가 서비스에 명시적으로 저장해야 한다. 10. 첫 버전의 완료 기준

시나리오 확인할 동작
공고 등록 URL·이미지·텍스트 원문을 지원 건에서 다시 볼 수 있고, 문항·조건을 수동으로 수정할 수 있다. 날짜 미상·상시채용을 구분하며 모르는 마감 시각을 만들어 넣지 않는다.
작성과 저장 작업 중 내용의 자동 저장과 명시적 버전 저장을 구분한다. 실패한 저장을 성공으로 표시하지 않고 입력을 유지해 재시도할 수 있다. 첫 버전의 글자 수는 공백 포함·제외를 함께 보여 주며 채용 사이트의 별도 계산 규칙까지 보장하지 않는다.
비교와 복원 작성 중 내용과 저장본 또는 선택한 두 저장본을 문항별로 비교한다. 문항 추가·삭제·순서 변경을 구분한다. 선택한 문항 복원 시 그 문항에만 새 버전이 생기고 이전 버전은 재현할 수 있다. 문항별 그래프·초안·번호가 분리되며 다른 문항은 바뀌지 않는다.
기업별 분리 다른 지원 건으로 복제한 글을 수정해도 원래 지원 건의 내용·이력·제출본이 변하지 않는다.
제출본 지정 시점의 문항·답변·조건·공고 맥락을 고정한다. 이후 작성이나 공고 변경에도 유지하며 재지정 이력을 남긴다. 제출본 지정만으로 외부 사이트 접수 성공을 표시하지 않는다.
상태와 일정 지원 상태와 마감·면접·과제 일정을 직접 수정하고 목록과 기본 캘린더에서 같은 정보를 본다. 날짜가 없는 건은 날짜 미확인 목록에서 찾을 수 있다. 외부 캘린더 동기화와 알림 발송은 포함하지 않는다.
AI 맥락 전달 지원 건·문항·답변 버전을 함께 식별해 관련 공고·확인된 경험·평가 기준 버전과 전달한다. 응답이 해당 문항의 원본 버전과 연결되며 다른 문항에 적용되지 않는다. 불필요한 다른 지원 건과 전체 버전 이력을 보내지 않는다.

유료 주간 추천은 지금 설명만으로는 약하다

사용자 본인도 이미 GPT 예약으로 비슷한 결과를 받고 있다. 추천 목록을 예쁘게 전달하는 정도라면 결제 이유가 부족하다.

사용자는 주간 추천을 지금은 넣지 않기로 했다. 이후 검토할 때는 새로 발견한 적합 공고, 이미 본 공고와 중복 제거, 경력·지역·고용 형태 같은 제외 조건, 마감 확인, 지원 건 생성까지 비교한다. 추천 때문에 실제로 지원한 건과 탐색 시간 감소가 먼저다. 가격은 이 결과를 본 사용자에게 검증하고 결제 화면은 뒤로 미룬다.

무지출과 자동화·음성 면접을 동시에 보장하기 어렵다

홈서버가 있어도 외부 API 사용료가 없어지지는 않는다. 개인 GPT 구독을 서비스가 호출하는 API 예산으로 가정해서도 안 된다. 음성 기능은 긴 세션과 반복 연습 때문에 비용이 커질 수 있다.

첫 경로는 사용자의 ChatGPT 이용 환경과 MCP 연결 조건을 확인한다. 결과 쓰기가 불가능한 계정이라면 수동 저장까지의 작업 시간을 측정한다. 이후 서비스 API를 추가할 때에는 별도로 호출 비용과 사용자당 한도를 정한다. 음성은 짧은 제한 세션으로 실제 분당 비용과 사용 빈도를 측정한 뒤 제공량을 정한다. 외부 사용자에게 무제한 무료 AI를 약속하지 않는다.

한 번에 전 과정을 만들면 핵심 검증이 늦어진다

공고 수집·추천, 자소서 편집, 캘린더, MCP, 음성은 각각 오류와 운영 부담이 있다. 모두 넣으면 사용자가 무엇 때문에 돌아오는지도 알기 어렵다.

권고: 처음에는 작성 → 변경점 확인 → AI 피드백 → 채택한 수정안을 새 버전으로 저장 → 제출본 확인을 완결한다. 일정은 이 흐름을 보조하는 최소 기능으로 둔다. 면접은 제출본이 쌓인 뒤, 유료 추천은 기존 예약보다 좋은 결과를 낸 뒤 확장한다.

포트폴리오를 위한 복잡성이 실사용을 방해할 수 있다

분산 구조나 병합 알고리즘을 늘리는 것보다 저장 유실이나 잘못된 제출본 표시를 해결하는 일이 먼저다. Docsa에서 이미 한 작업을 새 프로젝트의 성과처럼 재사용하면 기여 범위도 흐려진다.

권고: 문제 발생 조건, 대안, 선택 이유, 변경 전후 측정, 남은 한계를 기록한다. 실제 사용 중 생긴 문제만 트러블슈팅으로 작성한다.
