# 경쟁력 검토와 따로 논의할 의문점

작성일 2026-10-15 · 수정일 2026-10-23 · 공개 자료와 현재 기획에 대한 검토 · 사용자 검증 결과 아님

## 1. 현재 판단

개인 실사용 프로젝트로는 진행을 권고한다. 본인의 반복 작업을 줄이는지 직접 확인할 수 있고 Docsa의 버전관리 경험을 활용할 이유도 분명하다. 다만 범용 취업 플랫폼이나 유료 AI 서비스로 바로 확장하기에는 근거가 부족하다.

제품의 경쟁력 가설은 **국내 자소서의 문항별 수정 과정과 실제 제출본을 이어서 관리하고 익숙한 AI와 함께 쓰면서 면접 준비에도 재사용하는 경험**이다. 이 조합이 남들보다 편한지 입증해야 한다. 기능이 처음이라는 주장은 하지 않는다.

## 3. 약하거나 의문이 드는 부분

### 버전관리만 강조하면 사용 이유가 약하다

버전을 저장하는 데에는 문서 복제나 파일명 변경도 쓸 수 있다. 취업 준비자가 원하는 것은 이력의 개수보다 필요한 내용을 빨리 찾고 실수를 피하는 일이다. 제출본 찾기, 수정 전후 판단, 기업별 경험 재사용 중 어느 작업에서 확실히 편해지는지 먼저 확인해야 한다.

사용자는 무엇이 바뀌었는지 한눈에 보고 싶다고 밝혔다. Docsa에는 문단 단위 기록 비교와 프론트엔드 차이 표시가 이미 있다. 다만 새 자소서의 문항별 텍스트 구조에 맞는지와 실제로 한눈에 읽히는지는 확인해야 한다. 권고: 첫 화면에서 거대한 그래프를 보여 주는 방향은 피하고 작성 중 변경점, 두 버전 비교, 제출본 확인에 집중한다. 버전 저장이 관리 업무를 하나 더 만드는 수준이라면 범위를 줄인다. ### MCP와 평가 기준은 연결 방식이지 경쟁력의 증거가 아니다

평가 기준은 복사하기 쉽고 MCP 연결은 사용자에게 설정 부담을 준다. 연결 과정이 길거나 모바일에서 쓰기 어렵다면 복사·붙여넣기보다 불편할 수 있다. 사용자의 GPT가 자신을 더 잘 안다는 가정도 해당 대화에서 실제로 활용할 수 있는 자료에 한정된다.

첫 실사용 버전은 평소 쓰는 ChatGPT와 MCP로 연결하는 흐름을 선택했다. 사용 환경이 허용하면 MCP로 맥락을 제공하고, 쓰기 권한까지 확인되면 결과 저장도 연결한다. 공식 문서가 일반적인 읽기·쓰기 도구를 안내해도 개인 계정에서의 실제 사용 가능 범위는 연결 실험으로 확인한다. 연결이 어려우면 맥락 복사와 결과 저장으로 먼저 사용성을 시험한다. 이 대체 경로의 성공을 MCP 연동 완료로 간주하지 않는다. 어느 경로든 평소 GPT 피드백을 기준선으로 두고, 채택한 문장과 이유가 서비스에 자연스럽게 남는지를 본다. 외부 AI 연결과 나중의 서비스 내부 음성 면접에 같은 경험 자료를 전달할 경로가 필요하다. [맞춤 MCP 개발자 문서](https://developers.openai.com/api/docs/guides/custom-mcp-server) · [ChatGPT 맞춤 MCP 안내](https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt)

또 '내 GPT가 이미 나를 안다'는 전제는 GPT 형태에 따라 다르다. OpenAI는 맞춤 GPT가 저장된 기억이나 이전 대화를 사용하지 않는다고 안내한다. 일반 ChatGPT의 이어지는 대화 맥락과 맞춤 GPT의 지식 파일을 구분해 실제 피드백 품질을 측정해야 한다. [맞춤 GPT 안내](https://help.openai.com/en/articles/8554407-gpts-in-chatgpt)

사용자는 Plus 계정에서 MCP 연결을 우선하고 싶다고 정했다. 다만 서비스가 제공한 피드백 문구는 외부 AI에 전달되는 자료이지 모델의 상위 지침을 강제로 바꾸는 명령이 아니다. 또 같은 `v2`가 지원 건마다 있을 수 있으므로 특정 공고와 버전을 식별해야 한다. 사용자별 비밀 URL만으로 신원을 확인하는 방식보다 공통 연결 주소와 인증·권한 검사를 우선 검토한다. Plus 계정에서 필요한 도구가 실제 연결되는지 먼저 시험한다. [MCP 도구 설계](https://developers.openai.com/plugins/plan/tools) · [MCP 인증 안내](https://developers.openai.com/plugins/build/auth)

무료·유료 회원에게 피드백 프롬프트의 '품질'을 달리 주는 사업 모델은 권고하지 않는다. 좋은 기준은 쉽게 복사할 수 있고 의도적으로 낮춘 무료 피드백은 신뢰를 해칠 수 있다. 유료 범위를 검토할 때는 더 많은 지원 건, 자동 동기화, 저장·비교 편의, 음성 연습처럼 관찰 가능한 사용 가치와 실제 원가를 기준으로 삼는다.

### 내부 채팅에서 개인 구독을 쓰는 경로는 아직 제품 전제가 아니다

2026-10-23 공식 문서 확인으로 SIWC를 추가 검토한다. 개인용 오픈소스 자가 호스팅 절차와 공개·유료 웹서비스의 접근 신청을 구분해야 한다. 또한 SIWC는 기존 ChatGPT 대화·기억을 제공하지 않으므로, 내부 채팅으로 옮기면 사용자를 이미 잘 아는 GPT라는 이점이 자동으로 유지되지 않는다. 경험 자료를 다시 정리하는 부담까지 비교한다. [SIWC 개요](https://developers.openai.com/siwc/token-sharing-open-source)

현재 SIWC에서 hosted MCP/connectors는 미지원이다. 우리 애플리케이션의 도구 실행으로 연결하는 대안은 별도 검증이 필요하다. 일반 API의 기능 지원을 구독 사용 경로에도 적용하는 오류를 피한다. 접근 신청이나 실제 연결 시험은 수행하지 않았으며, 내부 채팅을 이유로 첫 버전의 외부 MCP 흐름을 미루지 않는다. [프리뷰 제한](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)

### 좋은 자소서의 기준을 주면 품질이 좋아진다는 가정은 검증이 필요하다

일반적인 문장 기준을 많이 주면 글이 획일적이거나 사실보다 그럴듯한 표현을 우선할 수 있다. 모든 문항을 같은 틀로 평가하는 것도 적절하지 않다.

사용자가 요청한 피드백 범위는 사실·경험 보존, 문항·직무 적합성, 문장 품질 모두다. 사실 보존은 다른 항목의 점수로 상쇄하지 못하는 필수 조건으로 둔다. 근거 없는 수치나 경험은 생성하지 않고 확인 질문으로 돌린다. 평가 기준의 버전과 피드백 대상 버전을 남긴다. 점수를 합격 가능성으로 해석하지 않는다.

### 공고·문항 자동 수집은 신뢰를 잃기 쉬운 기능이다

지원 페이지의 문항과 홍보 공고의 정보가 다를 수 있고 마감일이 변경되거나 이미지 일부가 누락될 수 있다. 틀린 마감일이나 글자 수 조건은 요약 문장 오류보다 영향이 크다.

권고: 자동 추출 후 확인을 거치고 원문 위치를 보여 준다. 필수 항목이 없으면 추측 대신 미확인으로 표시한다. 지원 직전에 실제 채용 사이트를 다시 확인하는 동선을 둔다. 사이트별 접근 조건과 수집 가능 범위는 자동화 전에 조사한다.

### 유료 주간 추천은 지금 설명만으로는 약하다

사용자 본인도 이미 GPT 예약으로 비슷한 결과를 받고 있다. 추천 목록을 예쁘게 전달하는 정도라면 결제 이유가 부족하다.

사용자는 주간 추천을 지금은 넣지 않기로 했다. 이후 검토할 때는 새로 발견한 적합 공고, 이미 본 공고와 중복 제거, 경력·지역·고용 형태 같은 제외 조건, 마감 확인, 지원 건 생성까지 비교한다. 추천 때문에 실제로 지원한 건과 탐색 시간 감소가 먼저다. 가격은 이 결과를 본 사용자에게 검증하고 결제 화면은 뒤로 미룬다.

### 무지출과 자동화·음성 면접을 동시에 보장하기 어렵다

홈서버가 있어도 외부 API 사용료가 없어지지는 않는다. 개인 GPT 구독을 서비스가 호출하는 API 예산으로 가정해서도 안 된다. 음성 기능은 긴 세션과 반복 연습 때문에 비용이 커질 수 있다.

첫 경로는 사용자의 ChatGPT 이용 환경과 MCP 연결 조건을 확인한다. 결과 쓰기가 불가능한 계정이라면 수동 저장까지의 작업 시간을 측정한다. 이후 서비스 API를 추가할 때에는 별도로 호출 비용과 사용자당 한도를 정한다. 음성은 짧은 제한 세션으로 실제 분당 비용과 사용 빈도를 측정한 뒤 제공량을 정한다. 외부 사용자에게 무제한 무료 AI를 약속하지 않는다.

### 한 번에 전 과정을 만들면 핵심 검증이 늦어진다

공고 수집·추천, 자소서 편집, 캘린더, MCP, 음성은 각각 오류와 운영 부담이 있다. 모두 넣으면 사용자가 무엇 때문에 돌아오는지도 알기 어렵다.

권고: 처음에는 작성 → 변경점 확인 → AI 피드백 → 채택한 수정안을 새 버전으로 저장 → 제출본 확인을 완결한다. 일정은 이 흐름을 보조하는 최소 기능으로 둔다. 면접은 제출본이 쌓인 뒤, 유료 추천은 기존 예약보다 좋은 결과를 낸 뒤 확장한다.

### 포트폴리오를 위한 복잡성이 실사용을 방해할 수 있다

분산 구조나 병합 알고리즘을 늘리는 것보다 저장 유실이나 잘못된 제출본 표시를 해결하는 일이 먼저다. Docsa에서 이미 한 작업을 새 프로젝트의 성과처럼 재사용하면 기여 범위도 흐려진다.

권고: 문제 발생 조건, 대안, 선택 이유, 변경 전후 측정, 남은 한계를 기록한다. 실제 사용 중 생긴 문제만 트러블슈팅으로 작성한다.

## 4. 실제 도움이 되는지 확인하는 실험

아래 규모와 기준은 제안이며 실험 결과가 아니다. 소규모 검증은 방향을 잡는 데 쓰고 통계적으로 입증된 성과로 표현하지 않는다.

| 변경점 확인·이전 표현 복원 | 수정 전후를 이해하고 복원하는 시간 | 무엇이 바뀌었는지 한눈에 찾고 원문을 잃지 않고 혼자 복원하는가 |
| 제출본 다시 찾기 | 정확한 제출본 찾기 | 어떤 버전인지 헷갈리지 않고 30초 안에 찾는가 |
| 일정 관리 | 중복 입력과 누락, 상태 변경 수고 | 기존 캘린더에 추가 관리가 생기지 않는가 |

제출본이 변하거나 저장한 글이 유실되면 다음 기능 추가보다 이를 먼저 해결한다. 서비스 사용 시간 증가를 몰입으로 해석하지 않고 필요한 작업을 마치는 시간을 본다.

### 다른 사용자 확인

목표에 맞는 취업 준비자 5명에게 2주 동안 실제 지원에 사용하도록 제안한다. 지원 활동이 없는 주는 재사용 판단에서 구분한다. 설명을 듣고 좋다고 말하는 것보다, 도움 없이 다음 지원 건을 추가하고 다시 비교 기능을 쓰는지를 관찰한다.

5명 중 3명 이상이 별도 재촉 없이 두 번째 지원 건을 관리하고 구체적인 시간 절약이나 실수 방지 사례를 설명하는 것을 다음 검증으로 넘어갈 잠정 기준으로 삼는다. 이 수치만으로 시장성이 입증되지는 않는다. 복잡하다고 느껴 기존 도구로 돌아가는 이유도 함께 기록한다.

### AI 방식 비교

같은 공고·문항·경험·초안을 사용해 다음을 비교한다.

| 비교 | 목적 |
| --- | --- |
| 평소 GPT 사용 vs GPT에 서비스의 맥락·평가 기준 추가 | 기준과 자료 정리가 실제로 도움이 되는지 확인 |
| 같은 맥락을 수동 전달 vs MCP 전달 | 연결 방식이 줄이는 시간과 설정 부담을 확인 |
| 이후 API 도입 시 가능한 한 모델·맥락·출력 형식을 맞춘 외부 AI vs 서비스 API | 제품 경로에 따른 품질과 편의 차이를 비교 |

모델이나 숨은 대화 맥락을 맞출 수 없으면 결과를 순수한 MCP/API 성능 차이라고 해석하지 않는다. 첫 실사용에서 최소 10개 문항을 반복 평가하고 출처를 가린 상태에서 사실·경험 보존, 문항·직무 적합성, 문장 품질을 모두 본다. 근거 없는 경험·성과가 제안되면 별도 실패로 기록하고, 구체성·본인 말투·수정 유용성도 살핀다. 본인과 문서 검토 경험자가 의견이 갈린 이유를 남긴다. 비용과 지연은 별도로 기록한다.

주간 추천은 후순위다. 유료화를 다시 검토할 때 현재 GPT 예약과 4주 동안 비교하는 실험을 제안한다. 적합 공고의 새 발견 수, 중복·마감 공고 비율, 실제 지원 수, 검토 시간을 기록한다. 공고가 적은 주의 결과도 숨기지 않는다.

## 5. 결정 사항과 구현 전 확인할 것

| 시점 | 확인할 것 | 처리 방향 |
| --- | --- | --- |
| 기획 결정 | 첫 사용자는 본인, 첫 버전에 AI 피드백 포함, 품질은 세 항목 모두 평가 | 와이어프레임에 작성·비교·피드백 채택 흐름 반영 |
| 기술 확인 전 | Plus 계정에서 평소 쓰는 대화에 맞춤 MCP 서버를 연결할 수 있고 필요한 자료를 실제로 조회할 수 있는가? | 실제 계정에서 읽기·쓰기 도구를 각각 시험하고 연결 흐름을 확정 |
| 구현 계획 | 현재 이용 환경에서 필요한 MCP 도구·인증·쓰기 권한을 쓸 수 있는가? | 작은 연결 실험 후 읽기만 되면 수동 저장, 연결이 막히면 맥락 복사·결과 저장으로 검증 |
| 코드 분기 전 | 기존 코드의 팀 기여·재사용 권한과 분기 범위는? | 원본을 보존하고 별도 저장소·데이터로 시작 |
| 실사용 후 | 다른 사용자에게도 MCP 연결이 복사·붙여넣기보다 쉬운가? | 연결 시간과 실패를 측정하고 API 경로의 필요성 판단 |
| 확장 검토 | 무엇에 결제할 의사가 있고 API 호출 비용을 얼마나 허용할 수 있는가? | 추천·음성·서비스 내부 피드백의 실제 효용과 원가를 확인한 뒤 결정 |

첫 실사용 버전의 제품 범위와 완료 기준은 기획서 v1.1의 6절·10절에 정리했다. 공고 자동 추출은 다음 단계이며 첫 버전의 수동 입력이 기존 방식보다 빠르다고 가정하지 않는다. 다른 사용자 범위, 서비스 내부 AI API, 유료화와 음성은 실사용 자료가 쌓인 뒤 판단한다. Plus 계정의 MCP 연결 가능성과 동작 범위는 작은 기술 실험으로 확인한다.
