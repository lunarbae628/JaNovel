# 공고 재사용과 사용자 AI 분석 계획

2026-11-25 · 설계안

같은 공개 공고를 여러 사람이 추가할 때 기존 추출 결과와 공유된 자소서 문항을 불러온다. 지원 건에서 기업·직무·문항 분석을 요청하면 연결된 사용자 AI가 근거를 읽고 분석한다. 현재 공고 가져오기는 백엔드에서 동작하고, 지원 건 저장과 계정은 브라우저 미리보기 단계다. [현재 구현](01-product-plan.md#현재-구현) · [공고 가져오기 명세](../../backend/README.md#api-문서)

## 이전 사용자가 입력한 공고 문항 자동 채움

1. 사용자가 URL이나 이미지로 가져온 공고의 **자소서 문항**을 채우고 **등록하고 작성**을 누르면 본인의 지원 건에 저장한다. 공개 공고를 식별할 수 있고 해당 직무에 저장된 문항 세트가 없으면, 빈 문항을 제외한 최초 입력을 다음 사용자의 자동 채움에 사용한다. 등록 화면에는 입력한 문항이 이후 자동 채움에 활용될 수 있음을 안내한다.
2. 다음 사용자가 같은 공고와 직무를 가져오면 공고 확인 화면의 **자소서 문항** 입력칸에 저장된 질문과 글자 수가 채워진다. 공식 원문에서 대조한 문항이 있으면 그 세트를 우선한다. 공통 문항을 채운 경우 **공고 문항 확인**과 원문 대조 안내, **실제 문항과 달라요** 버튼을 보여준다.
3. 사용자는 확인 화면과 등록 후 본인 지원 건에서 문항을 수정할 수 있다. **실제 문항과 달라요**를 누르면 올바른 문구나 글자 수를 선택적으로 제보할 수 있다. 제보는 사용자가 실제로 본 문항 버전에 연결한다. 공통 문항의 정정은 제보에서 원문이나 수정 근거를 확인한 결과로 반영한다.

자동 채움은 **공개 공고 ID + 모집 직무 ID 또는 공통**으로 묶는다. 같은 기업의 다른 회차는 별도 공고다. 이미지에서 공개 공고를 확인할 주소나 공고 ID를 확보하지 못한 경우 문항은 본인의 지원 건에 저장한다. 외부 직무 ID가 없는 경우에는 확인된 모집 분야를 공고 안에서 구분하고, 대응이 모호하면 사용자가 직접 직무를 확인한다. 최초 등록이 동시에 들어오면 DB에서 해당 범위에 문항 세트 하나를 생성한다.

지원 기록은 자소서 문항 없이 등록할 수 있다. 해당 지원의 첫 문항을 나중에 추가해도 공유 세트가 없는 같은 공고·직무의 자동 채움에 활용한다.

자동 채움에 쓰는 정보는 질문 텍스트, 순서와 문항 제한이다. 답변·메모·지원 상태와 첨부 원본은 각 지원 건의 소유권을 따른다. 계정별 등록 횟수와 문항 길이에 상한을 둔다. 개인정보나 외부 연락을 요구하는 문항은 공개 전 원문을 확인한다. 화면에서는 문항을 일반 텍스트로 출력하고, 인사이트에 전달할 때는 분석할 자료로만 취급한다. 검토에서 숨긴 세트는 이후 자동 채움 대상에서 뺀다. [OWASP 화면 출력 가이드](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html) · [OWASP LLM 입력 가이드](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)

공고 문항의 정정은 이후 등록 화면에 적용하고, 기존 지원 건과 작성 이력은 저장 당시의 문항 사본을 유지한다. 로컬 미리보기에서는 글자 수를 비워 두면 공통 문항과 확인 화면에 **미확인**으로 남고, 개인 작성 화면은 기존 기본값인 1,000자를 사용한다. 지원 건을 서버로 옮길 때 개인 작성 화면에도 제한 미확인을 표현한다. [공고 확인 화면](../../frontend/src/pages/Posting.jsx)

로컬 미리보기는 공고 상세 URL과 정규화한 직무명으로 문항을 찾는다. URL과 직무명이 같은 주소를 다음 회차에서 재사용하는 사이트는 별도의 공고 ID를 확보해야 회차를 구분할 수 있다. 등록과 제보 저장은 구현했으며, 서버 인증·공개 여부 확인과 제보 검토 화면은 운영 연결 단계에서 진행한다. [API 명세](../../backend/README.md#api-문서)

## 연결한 사용자 AI로 인사이트 만들기

티오 에디터의 인사이트에서 **직무 분석·문항 분석·기업 분석**을 확인했다. 직무 리포트에는 공고에서 읽은 요구 역량이 있었고, 문항 분석은 사용자가 문항을 입력하는 화면으로 이어졌다. 기업 리포트는 DART 원문 링크와 재무·경쟁사 분석을 제공했다. JaNovel에서는 기존 지원 건 상세 화면에서 세 분석을 요청할 수 있게 한다. [티오 기능 안내](https://tiokorea.com/) · [금융감독원 OpenDART 공시정보](https://opendart.fss.or.kr/guide/main.do?apiGrpCd=DS001)

| 기업 | 공고의 회사 식별 정보, 공식 회사 자료. DART 등록 법인이 확인된 경우 관련 공시와 조회 날짜 | 주요 사업과 최근 변화, 공고와 연결되는 내용, 근거 링크 |

| 문항 | 사용자가 확인한 질문과 해당 직무 분석 | 질문이 요구하는 답, 평가 의도에 대한 추론, 답변에 포함할 근거 |

가입 완료 화면에서 **내 AI 연결**을 제안하고, 설정에서 나중에 연결하거나 해제할 수 있게 한다. JaNovel 로그인과 모델 사용 권한을 별도로 확인한다. 첫 실험은 기존 개인 AI 설계처럼 로컬 실행 환경 한 가지로 요청부터 응답 저장까지 검증한다. ChatGPT 플랜 사용은 OpenAI가 지원하는 앱 형태와 별도 사용자 동의를 전제로 한다. 공개 호스팅 제품의 공식 연동은 참여 자격을 확인한 뒤 적용한다. [JaNovel 개인 AI 연결 검토](05-local-agent-chat-review.md) · [OpenAI 로컬 연동](https://developers.openai.com/siwc/token-sharing-open-source) · [OpenAI 공개 서비스 등록 안내](https://developers.openai.com/siwc/request-client-id)

공개 공고 추출은 JaNovel의 기존 서비스 모델을 사용한다. 인사이트는 사용자가 요청할 때 연결한 AI로 실행하고, 사용할 연결을 화면에 표시한다. 연결이 끊기거나 사용 한도에 도달하면 분석 상태를 안내한다. 같은 사용자의 같은 분석 유형과 입력 버전에는 기존 결과를 보여준다. 공고·선택 직무·문항·근거 자료가 바뀌면 새 버전으로 분석한다. 결과에는 입력 버전, 사용한 모델, 생성 시각, 출처를 남긴다. 분석은 요청자의 지원 건에서 조회하며 생성된 문항 해석은 공유 문항 저장 경로와 구분한다.

## 공고 추출 결과 저장과 Redis 도입 시점

### 공통 공고와 개인 지원 건의 참조 구조

`postings`에는 공개 공고의 최신 공통 본문·전형과 원문 확인 시각을, `posting_positions`에는 직무의 업무·요건·별도 마감을 저장한다. 사용자 지원 건은 `applications.posting_position_id`로 확인한 모집 직무를 참조한다. 기존 지원 건과 공개 공고를 식별할 수 없는 직접 입력·이미지는 참조 없이 저장할 수 있다. 공고 테이블의 데이터 적재와 지원 건 저장 API 연결은 이후 진행한다. [통합 V1 DBML](posting-reference-proposal.dbml)

개인 지원 건에는 등록할 때 확정한 회사·직무·마감·본문 항목·전형과 작성 문항을 보존한다. 공통 공고의 내용이 갱신돼도 개인 관리 정보와 작성 이력은 그대로 사용한다. 별도의 공고 원문 변경 이력은 필요해질 때 설계한다. 동일 URL이 새 모집 회차에 재사용될 수 있으므로 URL은 조회에 쓰고, 공고 식별 키는 확인한 모집 회차를 포함한다.

### 내 공통 자소서

지원 목록과 자소서 작성 화면에서 **내 공통 자소서**를 열어 문항·답변 초안·선택 글자 수를 하나의 세트로 작성하고 저장한다. 공고 확인 화면에서 문항이 비어 있을 때 직접 불러와 해당 지원 건의 개인 문항과 기본 작성안으로 복사한다. 저장한 공통 자소서가 없으면 공고 확인 안에서도 작성 화면을 열 수 있다. 복사 후 수정은 공통 자소서 원본에 반영되지 않는다. 복사된 개인 문항과 초안은 공개 공고의 자동 채움 대상에서 제외한다. 로컬 미리보기는 브라우저 프로필별 접근 키로 소유자를 구분하고, 실제 계정 동기화는 서버 인증 연결 이후 적용한다. [API 명세](../../backend/README.md#api-문서)

### 추출 결과 재사용

**첫 버전은 PostgreSQL에 추출 결과를 저장해 재사용한다.** 현재 Spring Boot 모듈러 모놀리스와 PostgreSQL 구성에서 병목은 원문 렌더링과 모델 호출이다. 같은 공개 공고를 DB에서 읽는 것만으로 두 작업이 빠진다. Redis는 PostgreSQL 조회가 실제 병목이 되거나 여러 인스턴스에서 읽기 트래픽이 늘 때 앞단의 공유 캐시로 도입한다. [현재 개발 환경](../../backend/compose.yaml) · [Redis cache-aside](https://redis.io/docs/latest/develop/use-cases/cache-aside/)

Redis에만 추출 결과를 두면 조회가 빠르고 TTL로 정리하기 쉽다. 만료나 메모리 퇴거 후에는 이미 읽은 공고도 다시 수집하고 모델을 호출해야 한다. PostgreSQL에 결과를 남기면 신선도가 끝난 뒤에도 본문 변경 여부를 비교하고, Redis가 필요해졌을 때 기존 결과를 그대로 채울 수 있다.

1. **공고 식별.** 공고 ID를 확인할 수 있는 경로에서는 플랫폼과 공고 ID를 사용한다. 나머지는 공고 식별에 필요한 쿼리를 유지한 대표 URL을 사용한다. 사용자가 붙여넣은 주소와 확인한 대표 주소를 연결할 수 있다.
2. **PostgreSQL 재사용.** 공고 전체의 추출 JSON, 본문 또는 이미지 입력 해시, 추출기 버전, 원문 확인·만료 시각을 저장한다. 유효한 결과가 있으면 원문 수집과 모델 호출을 건너뛴다. 만료 뒤에는 원문을 확인하고, 해시와 추출기 버전이 같으면 기존 JSON을 재사용한다. 실패나 일시적 접근 오류는 성공 결과의 유효 기간을 연장하지 않는다.
3. **동시 요청과 신선도.** 처음에는 동일 공고 요청이 하나의 추출 작업 결과를 공유하게 한다. 인스턴스를 늘릴 때는 공고 키별 DB 작업 소유권을 사용해 동시 미스에서도 모델 호출을 중복하지 않도록 한다. 초기 신선도는 진행 중 공고의 경우 몇 시간 단위로 시작하고, 마감이 가까우면 확인 간격을 줄인다. 실제 변경 빈도와 호출 절감 수치에 따라 조정한다.
4. **Redis 전환 조건.** DB 조회 p95, 연결 풀 대기, 재사용률, 원문·모델 호출 절감량을 먼저 기록한다. 도입 시 공고 서비스가 Redis에서 조회하고 미스나 장애면 PostgreSQL을 읽는다. Redis의 TTL은 원문 확인 유효 기간보다 길게 두지 않는다. 공유 문항이 바뀌면 별도 조회로 즉시 반영한다. 공고 추출 결과 갱신은 PostgreSQL 커밋 후 관련 Redis 항목을 비운다.

서비스 분리가 필요해지면 공고 서비스가 공고 ID와 수집 결과를 소유한다. 지원 건과 AI 분석 모듈은 그 서비스의 조회 계약으로 공고를 가져온다. 이 경계는 DB와 Redis 선택에 관계없이 유지된다.

## 구현 순서와 완료 기준

1. **공개 공고 재사용.** 통합 V1의 공고·직무 테이블에 추출 결과를 저장하고 링크 가져오기 서비스 앞에서 조회한다. 동일 URL 두 번째 요청은 원문·모델 호출 0회, 동시에 들어온 요청은 모델 호출 1회, 만료 후 본문 변경은 새 추출로 검증한다. 공고 번호가 다른 URL은 별도 결과를 반환한다.
2. **계정과 문항 자동 채움.** 실제 서버 인증과 지원 건 저장을 연결한다. 첫 사용자가 등록을 마치면 다음 사용자의 같은 공고·직무 확인 화면에 문항이 즉시 채워지는지 확인한다. 동시 최초 등록, 다른 직무, 식별되지 않은 이미지, 공식 문항 우선, 개인 수정 후 공통 문항 보존, 제보 대상 버전, 정정 후 기존 답변 보존을 검증한다.
3. **인사이트.** 사용자 AI 연결 한 가지와 직무 분석을 먼저 연결한다. 같은 입력 재요청, 연결 해제, 한도 초과, 다른 계정 조회 거절을 확인한 후 문항·기업 분석으로 확장한다.
4. **운영 측정과 Redis 판단.** PostgreSQL 경로를 부하 테스트하고 공개 운영 지표를 확인한다. Redis를 붙이면 TTL 만료, 장애 시 DB 조회, 갱신 후 오래된 결과 재노출, 인스턴스 간 중복 요청을 검증한다.

자동 테스트에는 가짜 공고 HTML·문항·모델 응답을 사용한다. 실제 공개 링크와 제공자 연결은 수동 확인에서 검증한다.
