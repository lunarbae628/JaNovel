### [2026-11-27] 비교 카드 반영 직후 강조와 스크롤이 이전 차이 표시에 가려지는 문제 수정
- **배경 및 문제점 (Problem):** 비교하기에서 문장 카드를 누르면 오른쪽 내 본문의 반영한 곳을 강조하고 칸 밖이면 그 자리로 스크롤해야 한다. 그러나 참고본과 다른 곳 표시는 입력을 멈추고 250ms 뒤에 다시 계산되고, 그 전에는 이전 표시를 편집 위치에 맞춰 옮겨 쓴다. 옮겨진 이전 표시가 반영한 자리와 겹치면 `MergeDraft`가 겹친 표시 중 앞의 것만 그려 반영한 곳 표시(`.flash`)가 빠졌다. 스크롤 효과는 `flash`가 바뀔 때 한 번만 실행되어, 250ms 뒤 강조가 나타나도 스크롤하지 않았다. 예시 본문의 카드 5개 중 4개에서 재현했다.
- **해결 및 변경 사항 (Solution):** `draftHighlights(marks, applied)`를 [선택 상태](../frontend/src/merge-state.js)에 두어, 반영한 범위와 겹치는 이전 차이 표시를 빼고 반영한 곳 표시를 넣는다. [작성 화면](../frontend/src/pages/Editor.jsx)은 이 결과를 `MergeDraft`에 넘긴다.
- **결과 및 트레이드오프 (Result & Trade-off):** 카드마다 반영 직후 강조가 반영한 범위 그대로 들어가고 다른 표시와 겹치지 않는 것을 `node:test` 회귀 테스트로 확인했다. 프론트 테스트와 빌드가 통과했다. 반영한 곳 주변의 차이 표시는 다음 재계산(250ms)까지 잠깐 빠진다. 실제 브라우저에서 스크롤 이동은 직접 확인하지 않았다.

### [2026-11-27] 지원 건 기본 정보·상태·항목·전형 수정과 삭제 API 추가
- **배경 및 문제점 (Problem):** 지원 건은 등록 뒤 바꿀 방법이 없어 회사·직무·마감을 고치거나, 상태와 현재 전형을 정하거나, 지원 건을 지울 수 없었다. 전형은 지원 건의 현재 전형이 참조하므로 목록을 통째로 다시 만들면 번호가 바뀌어 선택이 사라진다. 전형 순번 유니크 제약 때문에 순서를 바꾸는 중간에 순번이 겹친다.
- **고려한 대안 (Alternatives):** 전형도 공고 항목처럼 통째로 교체하는 방식은 현재 전형 선택이 매번 풀려 쓰지 않았다. 전형을 문항처럼 추가·수정·삭제·순서 변경 API로 나누는 방식은 프론트가 전형 편집 한 번에 여러 요청을 보내야 해 목록 하나로 맞추는 방식을 택했다. 순서 변경에 문항처럼 순번을 음수로 비우는 방식도 있었지만, 전형 제약은 이미 `DEFERRABLE`이라 검사를 미루는 쪽이 간단했다. 지원 건 삭제를 엔티티 `delete`로 하면 같은 영속성 컨텍스트에 읽어 둔 하위 엔티티가 지운 지원 건을 가리켜 플러시가 실패해 JPQL 삭제로 바꿨다.
- **해결 및 변경 사항 (Solution):** `ApplicationController`에 `PUT /api/applications/{id}`(회사·직무·마감·주소·원문 교체, 생략한 선택 값은 지움), `PUT .../progress`(상태와 현재 전형), `PUT .../sections`(공고 항목 통째 교체), `PUT .../stages`(번호가 있으면 이름·순서 변경, 없으면 추가, 빠지면 삭제), `DELETE .../{id}`를 두었다. 모든 변경은 지원 건 행을 `PESSIMISTIC_WRITE`로 잠근 뒤 처리한다. 상태는 전형 순서로 추측하지 않고 고른 대로 저장한다. `closed`로 바꾸면 그때의 현재 전형 이름을 `outcomeStageName`에 남기고, 종료를 풀면 결과 기록을 지운다. 현재 전형을 지우면 선택을 비운다. 다른 지원 건의 전형 번호나 겹치는 번호는 `STAGE_MISMATCH`(400)다. 전형 순서는 `SET CONSTRAINTS ... DEFERRED`로 검사를 미룬 뒤 저장하고 `IMMEDIATE`로 바로 검사한다. 공고 항목은 JPQL로 먼저 지운 뒤 다시 넣어 Hibernate가 삽입을 삭제보다 먼저 실행해 순번이 겹치는 문제를 피했다. 상세 응답에 `currentStageId`와 `outcomeStageName`을 더했다. `READ COMMITTED`에서는 지원 건과 전형 목록을 읽는 사이에 다른 변경이 커밋돼 응답이 두 시점을 섞을 수 있다는 Codex 리뷰 지적에 따라 상세 조회를 `REPEATABLE_READ`로 실행한다. 이 격리 수준이 실제로 적용되고 트랜잭션이 끝나면 `read committed`로 돌아오는 것을 확인했다. 요청의 번호는 `StrictId`로 정수만 받고, 문항 순서 요청도 이를 쓰게 바꿨다.
- **결과 및 트레이드오프 (Result & Trade-off):** `ApplicationEditControllerTests`로 기본 정보 수정과 잘못된 입력, 상태·현재 전형 변경과 종료 기록, 종료 뒤 전형 이름 변경 시 기록 유지, 공고 항목 교체, 전형 추가·이름 변경·연속 순서 변경·삭제, 현재 전형 삭제, 전형 번호 불일치, 지원 건 삭제와 하위 데이터 삭제, 다른 사용자 차단, 키 누락을 확인했고 전체 테스트가 통과했다. 서버를 띄워 `/v3/api-docs`에 다섯 경로와 응답 코드가 나오는 것도 봤다. 결과 옵션(`outcomeOptionId`)은 옵션 관리 API가 없어 아직 고를 수 없다. 목록 응답에는 현재 전형이 없다. 지원 건 삭제는 되돌릴 수 없어 프론트에서 확인 절차가 필요하다. 후속 계획: 지원 건 수정 API는 모두 마지막에 저장한 요청이 이긴다. 두 탭에서 엇갈려 저장하면 오래된 전형 목록이 그 사이 추가된 전형과 현재 전형 선택을 지우고, 기본 정보도 다른 탭의 수정을 되돌린다(Codex 리뷰 P1). 혼자 쓰는 서비스라 드물고, 버전을 프론트가 들고 다녀야 의미가 있어 프론트를 서버에 연결할 때 `applications`에 `version` 열을 두는 낙관적 잠금을 지원 건 수정·전형·항목·상태·문항 API 전체에 한 번에 적용한다. 상세 응답의 버전을 저장 요청에 함께 보내고, 서버 버전과 다르면 409로 거절해 프론트가 새로고침을 안내한다.

### [2026-11-27] AI를 JaNovel AI와 기기 연결의 두 갈래로 정리
- **배경 및 문제점 (Problem):** 사용자가 쓰던 개인 AI로 JaNovel 웹 채팅에서 첨삭받는 것이 목표였지만, ChatGPT·Claude 웹 구독을 외부 웹 채팅에서 쓰는 공개 통로는 없다. 1차로 둔 원격 MCP 첨삭은 ChatGPT Plus·Claude Pro 웹에서 조회와 후보 저장이 동작했지만 대화가 JaNovel 밖에 남았다. 개인 맥락 저장소를 어느 경로에 둘지도 섞여 있었다.
- **고려한 대안 (Alternatives):** 웹 MCP 첨삭을 무료 경로로 유지하는 안은 대화가 JaNovel 밖에 있어 사용자가 버린 기준에 맞지 않았다. 브라우저 확장과 브라우저 에이전트는 약관·안정성·프롬프트 인젝션 문제로 이미 제외했다. 맥락 가져오기를 1차에 넣고 경험 보관함만 따로 만드는 안은 무료 경로에서 이득이 작았다.
- **해결 및 변경 사항 (Solution):** AI는 JaNovel 웹 채팅에서만 쓴다. 기본은 AI API로 제공하는 유료 JaNovel AI이며, JaNovel이 개인 맥락을 보관해 초안과 첨삭에 쓰고 사용할수록 늘린다. 시작할 때 쓰던 ChatGPT·Claude의 기억에서 경험을 가져오는 기능을 선택으로 두고, 붙여넣기를 기본, MCP 커넥터를 편의 기능으로 하며, 항목별 미리보기에서 사용자가 남긴 항목만 저장한다. 붙여넣기에서 뺀 항목은 서버에 보내지 않고, MCP로 받은 내용은 임시 공간에 두었다가 빼거나 고르지 않은 항목을 지운다. 선택 갈래로 Codex app-server·Claude Code Channels 기기 연결을 두고, Sign in with ChatGPT는 승인되면 같은 갈래에 넣는다. 기기 연결은 전용 폴더에서 실행하고 폴더 밖 읽기·쓰기와 셸을 Codex 권한 프로필과 Claude Code 거부 규칙으로 막는다. 승인 자동 거부만으로는 승인 없는 읽기와 미리 허용된 도구를 막지 못한다는 Codex 리뷰 지적을 반영했다. 웹 MCP 첨삭과 MCP Apps 카드는 쓰지 않는다. MCP는 사용자 AI에서 데이터를 넣는 작업(맥락 가져오기, 공고 등록, 일정 추가)에 쓰고 수정·삭제와 자소서 본문·개인 맥락 읽기는 열지 않는다. MCP는 ChatGPT 무료 요금제와 배포 전에는 쓸 수 없어 붙여넣기 가져오기를 대체 경로로 유지한다. ### [2026-11-27] 비교 카드의 직접 수정 덮어쓰기·앞뒤 공백 중복·긴 본문 입력 지연 수정
- **배경 및 문제점 (Problem):** 프론트 리뷰에서 세 가지가 지적됐고 모두 재현했다. 첫째, 참고본 '저는 Python으로 개발했습니다.'와 초안 '저는 Java로 개발했습니다.'를 비교하다가 초안을 '저는 고객 상담을 맡았습니다.'로 고쳐도 카드는 예전 문장을 보여 줬다. 그 카드를 누르면 '저는 Python으로 상담을 맡았습니다.'가 되어 '고객'이 사라졌다. 직접 편집할 때 구절 범위만 옮기고 카드 내용과 선택은 그대로 두었기 때문이다. 둘째, 첫 줄 앞이나 끝 줄 뒤에 공백이 있는 초안은 비교를 시작하자마자 양 끝 공백이 두 배가 됐다. `createMergeState`가 문단에 이미 들어 있는 줄 안 공백을 본문 앞뒤에 다시 붙였기 때문이다. 셋째, 비교 중 한 글자를 입력할 때마다 렌더 중에 모든 문단 쌍을 다시 비교했다. 150문단 본문에서 한 문단을 고쳐도 63ms, 서로 다른 본문은 176ms가 걸렸다.

[선택 상태](../frontend/src/merge-state.js) · [문단 정렬](../frontend/src/comparison.js) · [작성 화면](../frontend/src/pages/Editor.jsx)
- **결과 및 트레이드오프 (Result & Trade-off):** 재현 조건마다 `node:test` 회귀 테스트를 추가했다. 직접 고친 카드는 숨겨지고 눌러도 본문이 그대로이며, 다른 곳을 고친 뒤 반영을 취소할 수 있다. 공백·들여쓰기가 있는 본문은 반영 후 취소하면 원문과 같다. 긴 본문은 한 문단 수정이 0.1ms, 서로 다른 본문이 약 30ms로 줄었다. headless 브라우저에서 수정 후 카드 재구성과 반영 취소도 확인했다. 대신 입력 후 250ms 동안은 표시와 카드가 이전 계산을 따른다. 문단이 아주 많은 본문에서 순서가 멀리 떨어진 문단끼리는 짝짓지 않는다. 반영한 카드가 하나라도 있으면 직접 고쳐 새로 생긴 차이는 카드로 만들지 않고 오른쪽 표시로만 보여 준다.

### [2026-11-27] 등록한 지원 건의 자소서 문항 추가·수정·삭제·순서 변경 API 추가
- **배경 및 문제점 (Problem):** 문항은 지원 건 등록 때만 저장할 수 있어, 공고에서 빠진 문항을 더하거나 잘못 추출한 문항을 고치고 지우거나 작성 순서를 바꿀 방법이 없었다. 순번에는 `(application_id, position)` 유니크 인덱스가 있어 순서를 한꺼번에 바꾸면 갱신 중에 순번이 겹치고, 동시에 두 요청이 문항을 더하면 같은 순번을 잡을 수 있었다.
- **고려한 대안 (Alternatives):** 문항 목록 전체를 한 번에 교체하는 `PUT`은 문항 번호가 바뀌어 이후 작성본·제출 답안과 연결이 끊기므로 쓰지 않았다. 유니크 인덱스를 `DEFERRABLE`로 바꾸는 방안은 V1 스키마와 DBML을 다시 고쳐야 해 순번을 임시로 음수로 옮기는 방식을 택했다. 삭제 뒤 순번을 앞으로 당기는 방안은 갱신 순서에 따라 충돌할 수 있고 얻는 것이 없어 빈 번호를 그대로 두었다.
